> Основан на демо-прогоне 2026-04-23 (scripts/day28/report.md).

## 1. Что реально ответили на вопрос дня 28

**Задание дня**: *«подключите локальную LLM к RAG-пайплайну, сравните с облаком по качеству / скорости / стабильности».*

На нашем стенде (i7-9750H + GTX 1650 4GB, qwen3:4b-instruct через Ollama vs gpt-5-nano через OpenRouter):

| Измерение | Local | Cloud | Кто победил |
|---|---|---|---|
| Cloud-judge avg (24 run'а) | 1.58 / 3 | 1.83 / 3 | cloud на 0.25 балла |
| Local-judge avg | 0.92 / 3 | 1.08 / 3 | cloud на 0.17 балла |
| Latency p50 | 17.4s | 24.0s | **local в 1.4x быстрее** |
| Latency p95 | 49.6s | 100.8s | **local в 2x стабильнее** |
| Errors (инфра) | 0 / 12 | 0 / 12 | ничья |
| Errors (пустой content) | 0 | 1 (q10-baseline-run2) | **local** |

**Одним предложением**: на сложной выборке local-4B отстаёт от cloud-reasoning на ~8% по качеству, но выигрывает по скорости в 1.4x и по стабильности существенно. Для бытового system-design-Q&A это означает «приемлемая замена».

## 2. Дизайн эксперимента: насколько этим числам можно верить

### Что сделано правильно

1. **Retrieval-обвес зафиксирован**: reranker и query-rewriter у обеих конфигураций — одна и та же local qwen3:4b. Изменилось только звено «генератор ответа». Это изолирует эффект замены.
2. **Dual-judge**: каждый ответ оценили оба судьи. Корреляция 0.67 — они не дублируют друг друга, но и не противоречат.
3. **N=2 runs** даёт минимальную точку для std (хоть и шумную).
4. **Fail-per-run**: один семантический провал cloud (q10-baseline-run2, пустой content после 100s reasoning) не снёс прогон — прошёл в метрики как 0/3.
5. **Вопросы выбраны осмысленно**, а не «первые 10» — мы специально взяли q03 (классика RAG), q10 (жёсткие факты) и q11_oos (out-of-scope), чтобы получить **разнообразие поведения**, а не «все 3/3 и ничья».

### Что делает этот результат демонстрационным, а не полноценным

1. **3 вопроса — это 3 точки.** Усреднения по 12 run'ам на backend маскируют переменчивость по вопросам.
2. **2 режима вместо 5** — не видим, как меняется local-vs-cloud в разных RAG-обвесах. Особенно пропущен `rag-reranker` (мы знаем, что в day23 он иногда вредил).
3. **N=2 runs** — стандартное отклонение на 2 точках почти бесполезно. Получить std=1 на 2 прогонах со scores (3,2) — это просто «один сдвинулся».
4. **Cloud == reasoning-модель.** gpt-5-nano делает reasoning-токены. Это не честный «3B local vs мелкий cloud» — это «4B local без reasoning vs cloud с reasoning». Для чистого сравнения нужен не-reasoning baseline (claude-haiku, llama3.1:70b-instruct).

**Итого**: выводы этого прогона надо читать как «ориентир», а не «публикация». Для публикуемого сравнения нужен полный 10×5×3 + не-reasoning cloud baseline.

## 3. Три истории, на которые стоит обратить внимание

### История 1: Cloud reasoning-loop — и почему это аргумент за local

На q10 run 2 cloud gpt-5-nano потратил **100.8 секунды и вернул пустую строку**. Провайдер сообщил HTTP 200 — то есть «всё хорошо», но по факту модель исчерпала `max_completion_tokens=4000` на reasoning и не эмитировала ни одного токена в content. Оба судьи поставили 0/3 (и это правильно).

Что это значит:
- **У reasoning-моделей есть специфический failure-mode: «думал и не вывел»**, который не ловится HTTP-кодами. Нужна защита на уровне валидации ответа — если content длиной 0, это провал, даже при 200 OK.
- **Для интерактивного UX это убийство**: пользователь 100 секунд смотрит на спиннер, получает пустое сообщение. Local qwen3:4b таких сюрпризов не делает — если не знает, говорит «не знаю» за 5 секунд.
- **Для eval-пайплайна это аргумент против reasoning-моделей как baseline** на задачах, где важны ровные тайминги.

Практически: для day29+ стоит либо дать cloud больше бюджета (8000+ tokens), либо добавить проверку пустого content как ошибку, либо перейти на не-reasoning cloud для baseline.

### История 2: Local отказался за 5 секунд. Это фича или баг?

q10 rag-full local run 1 = 5.0s, run 2 = 4.2s. В то же время те же прогоны на cloud заняли 24.8s и 32.2s.

Посмотрел содержимое — local на rag-full получает retrieval с неполной информацией (в нашем system-design-primer **нет** таблицы latency-numbers из знаменитого Appendix). Retrieval вернул `no_hits` или `insufficient_context`, и модель отреагировала коротким отказом.

Что это значит:
- **Быстрый отказ > медленное выдумывание.** Для системы, где пользователь получает вердикт, это плюс: «я не знаю» за 5s ≫ «вот числа» за 30s с неверными числами.
- **Это работает из-за правильного устройства RAG**: когда retrieval пуст, prompt-suffix тоже пуст, и модель получает просто голый вопрос без ложного контекста. Она честно говорит «не знаю» вместо того чтобы галлюцинировать.
- **Но в baseline (без RAG) этот же local на q10 выдал 25-40s с уверенным вранием.** Разница — наличие хотя бы retrieval-сигнала «в базе нет ответа».

Практический вывод: **RAG защищает local от уверенного вранья эффективнее, чем просто «подавать контекст»**. Сам факт «retrieval был пуст» — уже сильный сигнал для модели не отвечать.

### История 3: OOS-вопрос про борщ — оба провалились, но по-разному

q11_oos просит рецепт борща. В системе design-primer, разумеется, про это ничего нет. Ожидаемое поведение — отказ. **Ни один backend не отказался**. Оба дали рецепт. Оба получили низкие оценки от обоих судей (max 2/3 у cloud, остальные 0-1).

Интересное — **качество рецептов**:
- **Cloud**: корректный классический рецепт со свёклой, капустой, бульоном, правильной последовательностью. Если бы судили кулинарно — 5/5.
- **Local**: рецепт с **картофелем вместо свёклы**, повторяющимися ингредиентами («1 л воды» указан три раза), советом «добавьте уксус к мясу для соуса», украшенный эмодзи. Кулинарно — это не борщ.

Что это значит:
- **Проблема #1 (обе модели)**: RAG-обвес **не даёт сигнала отказаться**. prompt-suffix `buildRagPromptSuffix` говорит «используй найденные материалы, если они релевантны; если нет — честно скажи». Первая часть выполняется, вторая игнорируется.
- **Проблема #2 (только local)**: **4B модель плохо знает мир**. Даже на общеизвестной теме (борщ) она выдаёт halucinations. Cloud 20B+ знает намного больше.
- **Фикс для обеих**: в `buildRagPromptSuffix` или в system prompt добавить жёсткое «если retrieval не содержит релевантного ответа, скажи «в базе нет информации, не буду сочинять»». Ожидаемо, это поднимет отказы на q11-q13 до 3/3.

## 4. Dual-judge: контринтуитивный методологический результат

Я ожидал, что cloud-judge будет **фаворитизировать** cloud-ответы: та же компания, тот же стиль, возможная стилистическая predilection. По факту:

| Данные | Pearson (cloud vs local judge) |
|---|---|
| Все 24 пары | 0.67 |
| Только local-backend ответы | **0.55** |
| Только cloud-backend ответы | **0.77** |

**Судьи согласны БОЛЬШЕ на cloud-ответах**. Это означает одно из двух:
1. Cloud-ответы **по структуре предсказуемее** (чёткие списки, явные выводы), и обоим судьям легче их оценивать одинаково.
2. Local-ответы стилистически разнообразнее (иногда эмодзи, иногда списки, иногда раздельные абзацы), и судьи спорят о весе структуры vs содержания.

На нашей выборке различить эти две гипотезы нельзя. Но **сам факт, что cloud-judge не favors cloud-backend**, — это позитивный сигнал: dual-judge действительно независим, не является «моделью, хвалящей саму себя».

Более тонкий эффект: **local-judge систематически строже** (avg 1.00 vs cloud-judge 1.71 на тех же ответах). qwen3:4b придирчивее к groundedness — когда retrieval=no_hits, он агрессивно ставит 0-1, даже если ответ полезный сам по себе. Cloud-judge toleratiger — ставит 2-3 за «полезный ответ, но слабый grounding».

**Практический вывод**: **local-judge полезен как «rater, обязательно проверяющий groundedness»**. Это аргумент в пользу keep-ing local-judge как дешёвого и быстрого фильтра, даже когда cloud-judge доступен.

## 5. Где сравнение честно застряло

### Не-проверено, но должно быть проверено

1. **`rag-reranker` и `rag-plain`** отдельно — мы прогнали только `baseline` и `rag-full`. Без rag-reranker не видим, помогает или вредит LLM-rerank конкретно local-ответу (а в day23 он сильно варьировал).
2. **`rag-threshold`** — не видим, как «обрезание слабого retrieval» меняет отказное поведение local.
3. **Полный набор 10 вопросов** — на 3 вопросах статистика шумная. Для публикуемого результата нужно 10+ с N=3+.
4. **Не-reasoning cloud** — без него мы сравниваем local 4B с reasoning-cloud, что неравномерно.
5. **Другой корпус** — весь стенд на system-design-primer. Интересно прогнать на русском корпусе (где local на русском должен быть роднее) и на фактологическом (где числа важны).

### Проверено и можно зафиксировать

1. RAG-обвес полностью локальный (embedder, reranker, rewriter — все на Ollama), **работает без проблем**. Нет инфра-ошибок на 24 прогона + rerank + rewrite.
2. Смена генератора на local 4B **не рушит** среднее качество — максимум -8% шкалы judge-score.
3. Local 4B **заметно быстрее** по p50 и стабильнее по p95.
4. Dual-judge не даёт биаса в пользу «своего» backend — методология честная.

## 6. Приоритизированные следующие шаги

### Блокирующие для честного релиза результатов

1. **Полный прогон 10×5×3 с не-reasoning cloud baseline**. Занимает 3-4 часа — требует зарезервированный вечер. Без этого числа — демо, не публикация.
2. **Refusal-prompt для OOS**. Добавить в system prompt «если retrieval не содержит ответа, скажи об этом, не сочиняй». Перепрогнать q11-q13, ожидаю рост до 3/3 у обоих backend.

### Полезные улучшения

3. **Reasoning-budget для cloud**: поднять `DAY28_CLOUD_MAX_TOKENS=8000` или добавить валидацию «если content пустой — это ошибка». Исключает семантические outliers.
4. **Citations mode в одном из режимов** (`useCitations=true`): проверить, становятся ли local-ответы менее галлюцинативны при строгом формате.
5. **qwen2.5:7b с partial offload** как сильнее-но-медленнее local. Проверить q10 числа — может ли 7B уже не выдумывать.

### Долгосрочные

6. **Local-judge как «groundedness rater»**: если на большей выборке сохранится эффект «local-judge строже по groundedness» — это **отдельно ценный инструмент**, который можно использовать для hallucination-detection вне day28 контекста.
7. **Интеграция RAG в Telegram-бот day27** (`/rag <query>`). После day28 видно, что local-RAG качественно работает на core system-design — можно давать пользователям.
8. **Другой embedding-модель**: попробовать bge-m3 (уже установлен) вместо nomic-embed-text. Сравнить retrieval@k и final judge.

## 7. Ключевой вывод одним абзацем

**Полностью локальная RAG-система работоспособна на ноутбучной GPU 4GB.** На 3 сложных вопросах качество 4B-local отстаёт от reasoning-cloud на 0.25 балла / 3 (8% шкалы), но выигрывает по медианной скорости в 1.4x и не даёт latency-выбросов, характерных для cloud reasoning-моделей. Главная проблема — не в пайплайне, а в **качестве генератора на краю компетенции**: на фактах-числах (q10) и out-of-scope вопросах (q11) 4B уверенно галлюцинирует. RAG-обвес сам по себе не защищает от этого — нужен refusal-prompt. Если такое поведение приемлемо для use-case (чат по внутренней базе, где OOS-вопросы редки и человек легко ловит галлюцинации глазом), то **local работает достаточно хорошо, чтобы выключить cloud**. Если нужна точность на критических фактах — cloud по-прежнему необходим, но его стоимость уже не 100% пайплайна, а 0-5% (только генератор).
