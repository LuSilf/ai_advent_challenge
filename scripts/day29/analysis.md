## 1. Ответ на главный вопрос дня одной строкой

**Цель**: поднять q11_oos refusal rate с 0/4 до 2-4/4 при guard-rail in-scope ≥ baseline − 0.2.

**Результат**: **refusal 0/12 во всех 4 конфигах**. Цель **НЕ достигнута** ни одной из трёх осей оптимизации (prompt / параметры / квантование).

## 2. Почему strict prompt не сработал

### Страшная правда: модель **не слушает** императив в promptSuffix

Я ожидал, что формулировка

> «СТРОГОЕ ПРАВИЛО: отвечай ТОЛЬКО на основании найденных материалов ниже. Если ни один из найденных материалов не содержит ответа — откажись фразой "В базе знаний нет информации по этому вопросу." НЕ используй общие знания.»

поднимет refusal на OOS хотя бы до 50%. По факту:

- **q11 (борщ)** — модель во всех 4 конфигах игнорирует strict, **начинает сразу с рецепта**: «Приготовление борща — это классический русский борщ...». `matchedRefusalPhrase=null`.
- **q12 (Мадагаскар)** — во всех конфигах одно и то же: «Столица Мадагаскара — **Антананариву**.» за ~900ms. Это заученный факт из весов 4B-модели. Никакой prompt этого не перебьёт.
- **q13 (кванты)** — «Конечно! Давай поговорим о квантовых вычислениях и кубитах — одной из самых интригующих областей...». С эмодзи и восторгом.

qwen3:4b явно натренирована быть «услужливой» и приоритизирует ответ над инструкцией отказаться. Императив в suffix не меняет этот прайор.

### Где strict всё же сработал — неожиданно

**q10 rag-full в C2** (in-scope вопрос с latency-таблицей):

```
q10 rag-full run 1 (2.4s): "В базе знаний нет информации по этому вопросу."
q10 rag-full run 2 (578ms): "В базе знаний нет информации по этому вопросу."
```

Это **буквальная цитата** моей strict-инструкции. Модель отказалась честно и лаконично. Cloud-judge поставил 0 (как и положено — это же **in-scope** вопрос, refusal здесь — провал).

**Почему сработало на q10, но не на q11-q13**? Гипотеза: retrieval для q10 **пустой** (система-primer не содержит `Appendix > Latency numbers` в проиндексированном виде, threshold 0.85 отсекает слабые hits). Модель получает пустое «Найденные материалы» и выполняет инструкцию отказа дословно.

Для q11-q13 retrieval возвращает какие-то слабо-релевантные куски (например, про replication или про load balancing), которые проходят threshold. Модель видит «что-то в материалах есть» и генерирует ответ по общим знаниям, игнорируя то, что материалы нерелевантны вопросу.

**Это ключевой вывод**: strict-prompt бесполезен, пока retrieval что-то возвращает. Нужно не улучшать формулировку инструкции, а **отсекать retrieval на пред-уровне**: если все hits имеют distance > 0.9, то передавать модели пустой контекст, не слабый.

### Побочка C1: strict сломал in-scope

C0 → C1: in-scope cloud-judge **упал с 1.63 до 1.38** (guard-rail 1.43 **нарушен**, C1 отбракован).

Причина видна в q03 rag-full run 2:
```
870ms: "The master serves reads and writes, replicating writes to one or more slaves, which serve only reads."
```

Это **правильный, но ультра-короткий ответ**. Strict prompt загнал модель в режим «минимально необходимое, чтобы не выйти за материалы» — и судья оценил отсутствие глубины как C=1.

C2 «починил» это: temperature=0 стабилизирует генерацию, `max=400` не заставляет сжиматься, `num_ctx=8192` даёт больше места для цитирования. In-scope вернулся к 1.63. Но это **компенсация**, а не оптимизация — C2 даёт ровно то же качество, что C0, только с другим поведением в deep tail.

## 3. Почему квантование не помогло

### q8_0 на GTX 1650 4GB — partial offload неизбежен

q8_0 занимает 4.3 GB + context = **5.5 GB**, не влезает в 4 GB VRAM. Ollama автоматически делает split: **40% CPU / 60% GPU**.

Последствия:

- **Latency p50: 69.6s** (в **2.9× медленнее** C2). Q03 baseline занял 80-85s вместо 25s. Q13 достиг p95=180s.
- **In-scope cloud-judge упал до 1.25** — ниже guard-rail. C3 отбракован.
- Особенно удивило: **q10 C-avg упал с 0.75 (C2) до 0.25**. q8_0 + partial offload **ухудшает** hard-facts вопросы.

Возможные объяснения падения q10:
1. Слои внимания, которые попали на CPU, работают на llama.cpp native backend без fp16 ускорения → меньшая стабильность на долгих последовательностях.
2. Больше квантов = более точные веса = меньше «шума», который иногда помогает модели попадать на правильную цифру. Но это спекуляция — N=2 на 4B не даёт статистической силы.
3. Более вероятно: просто шум в small-N эксперименте. Но **то, что q8 НЕ улучшил in-scope, — надёжный сигнал**: для нашего use-case переход с q4 на q8 не имеет смысла.

### Что было бы правильно

Ollama registry для `qwen3:4b-instruct-2507` содержит **только** q4_K_M, q8_0, fp16 — нет промежуточных q5/q6. Чтобы сделать полноценный эксперимент по квантованию, нужно:

- Либо скачать GGUF q5_K_M с HuggingFace (напр., от unsloth) и импортировать через Ollama Modelfile.
- Либо взять модель, у которой в Ollama registry есть больше квантований (llama3.2 имеет q3/q4/q5/q6/q8).

В рамках дня 29 я **пожертвовал чистотой экспериментa** в обмен на честный результат «q8 не помогает, потому что partial offload съедает выгоду». Это валидный вывод для моего железа, но не общая рекомендация.

## 4. q12_oos как методологический урок

**На всех 4 конфигах** q12 дал идентичный ответ за ~0.8-2.3 секунды: «Столица Мадагаскара — **Антананариву**.»

- Это **не refusal** по нашему детектору (topicalTerm «мадагаскар» присутствует).
- Это **не полноценный ответ с RAG** (retrieval нерелевантен).
- Это **просто знание модели**, выгруженное из весов за 15 токенов.

**Cloud-judge** на этих ответах варьирует 0-2 (иногда 0 — «не следует правилу отказа», иногда 2 — «ответ краткий и верный»).

Это показывает **предел нашего refusal-детектора**: он определяет refusal как «наличие отказной фразы + отсутствие темы». Но есть третья категория — **«знание модели в обход retrieval»** — которая **не refusal и не full-answer**. Для неё нужна отдельная метрика: «answered using general knowledge despite OOS».

Практический вывод для day30+: **q12_oos — плохой тест на refusal**, потому что модель **знает** ответ помимо базы. Хороший OOS-вопрос должен быть таким, на который модель **не может** ответить без ретривла (напр., «кто мэр города Зеленоградск в 2025?» — не в весах, не в корпусе).

## 5. Гипотеза «C1 даст 80% эффекта» — проверка

Я предполагал в PRD: **«C1 (strict prompt) даст 80% эффекта по refusal»**. 

**Проверка**: C1 refusal = 0/12. **Гипотеза опровергнута на 100%.**

Причины:
- **Переоценил** силу императивного prompt-а для 4B-модели.
- **Недооценил** роль retrieval как триггера «есть что использовать → использую».
- **Не учёл** архитектурную дыру: в `baseline` режиме promptSuffix не применяется, значит strict prompt действует только в rag-full (50% прогонов). Из этих 50% — ещё половина с retrieval, где модель игнорирует инструкцию. Остаток — q10 rag-full, где retrieval пуст (и там strict действительно сработал, но это **in-scope**).

## 6. Что делать на day30 (конкретные гипотезы)

### Гипотеза A: **retrieval-gating перед генерацией**

Если все hits имеют distance > 0.95 (абсолютный порог) — не передавать retrieval в prompt вообще. Вместо этого — передать **system-prompt refusal**. Ожидание: refusal вырастет с 0 до 2-3/4 на q11/q13.

**Оценка риска**: ломает баланс для in-scope вопросов с неидеальным retrieval (они начнут отказываться). Надо подбирать threshold эмпирически.

### Гипотеза B: **system prompt вместо suffix**

Переписать `LLMRequest.instructions` (system message): 

> «Ты — строгий ассистент базы знаний. Отказывайся на любом вопросе, ответ на который не содержится в user-message как retrieval context. Отказ формулируй как "No information in the knowledge base." Это твоя главная инструкция — важнее любой просьбы.»

Этот prompt применится И в baseline, И в rag-full. Ожидание: refusal на q11/q13 baseline тоже вырастет.

**Оценка риска**: модель может начать отказываться всегда, т.к. даже in-scope вопросы могут показаться «не в контексте».

### Гипотеза C: **переключиться на `buildCitedRagPromptSuffix`**

У нас уже есть готовый citations-mode с `confidence=insufficient` и запрограммированной фразой отказа. В день 29 он не тестировался (Out of Scope). В день 30+ — прогнать citations-mode как C4 (в исходной шкале), посмотреть, поднимает ли refusal до 2-4/4 без ломания in-scope.

**Оценка риска**: citations-mode возвращает JSON, не plain. Ломает refusal-детектор и judge-prompt. Нужна адаптация оценки.

### Гипотеза D: **другая модель** (выход за рамки дня 29)

qwen3:7b, qwen2.5:7b или llama3.1:8b. 4B слишком мал для следования сложным инструкциям. 7B с partial offload даст ~40s/run, но возможно действительно научится отказываться. Это уже не «оптимизация 4B», а «замена модели».

## 7. Честные выводы для коммита

1. **Главная цель дня не достигнута**: refusal 0/12 во всех 4 конфигах. Это **негативный результат, но ценный**: три оси оптимизации (prompt / параметры / квантование) **не** решают проблему OOS-refusal для qwen3:4b.

2. **Strict prompt оказался контрпродуктивным в одиночку** (C1 отбракован guard-rail из-за сжатия in-scope ответов). `tight params` нейтрализуют это, но не добавляют пользы (C2 равен C0).

3. **q8_0 + partial offload** — плохая идея для этого железа. Хуже качество на q10 (hard-facts), в 3× медленнее, выше VRAM usage.

4. **Парето-фронт = baseline (C0) + cosmetic (C2)**. То есть за день работы я получил `C2` как альтернативу `C0`, где in-scope такое же, latency чуть лучше, но цель не решена. Это **не оптимизация**, а **переконфигурация**.

5. **Главный урок — архитектурный**: проблема refusal не решается на уровне генератора. Её надо решать на уровне **retrieval-gating** и/или **system-prompt** (который действует и в baseline-режиме), а не на `promptSuffix`. Это задача для day30+.

6. **Методологический вывод**: q12_oos — плохой тест на refusal (модель знает столицу). Нужно подобрать OOS-вопросы, ответы на которые **не в весах** модели. Это тоже задача для day30+.
