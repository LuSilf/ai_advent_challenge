# Plan: Реестр моделей и учёт стоимости

> Source PRD: `.ai/prd/model-registry.md`

## Архитектурные решения

Решения, действующие во всех фазах:

- **Схема**: таблица `models` (id, name, input_price, output_price, context_size) и таблица `model_roles` (role, model_id FK → models) — создаются в `initDb()` рядом с существующими таблицами
- **Роли**: три фиксированных значения — `chat`, `title`, `facts`
- **Предзаполнение**: 7 моделей и 3 дефолтных маппинга через `INSERT OR IGNORE` при инициализации БД
- **REPL-команды**: `/models`, `/roles`, `/set_model <роль> <model_id>`
- **Стоимость**: вычисляется по формуле `(input_tokens / 1_000_000) * input_price + (output_tokens / 1_000_000) * output_price`

## Phase 1: Таблица моделей и просмотр

**User stories**: 4, 6

### Что построить

Добавить таблицу `models` в SQLite и предзаполнить её 7 моделями при инициализации БД. Реализовать функции получения модели по id и списка всех моделей. Добавить REPL-команду `/models`, которая выводит таблицу моделей с ценами и размером контекста.

### Критерии приёмки

- [ ] Таблица `models` создаётся при `initDb()` с полями id, name, input_price, output_price, context_size
- [ ] 7 моделей из PRD вставляются через `INSERT OR IGNORE`
- [ ] Функция получения списка всех моделей возвращает корректные данные
- [ ] Функция получения модели по id возвращает модель или null
- [ ] Команда `/models` выводит отформатированную таблицу моделей
- [ ] Тесты покрывают предзаполнение, получение по id, получение списка

## Phase 2: Маппинг ролей и управление

**User stories**: 2, 3, 5

### Что построить

Добавить таблицу `model_roles` с дефолтными маппингами (все роли → `openai/gpt-5-nano`). Реализовать получение модели по роли, смену модели для роли с валидацией существования model_id. Добавить REPL-команды `/roles` и `/set_model`.

### Критерии приёмки

- [ ] Таблица `model_roles` создаётся при `initDb()` с внешним ключом на `models`
- [ ] 3 дефолтных маппинга вставляются через `INSERT OR IGNORE`
- [ ] Функция получения модели по роли возвращает полные данные модели
- [ ] Функция смены модели для роли валидирует что model_id существует в таблице `models`
- [ ] Команда `/roles` выводит текущий маппинг ролей
- [ ] Команда `/set_model chat deepseek/deepseek-v3.2` меняет модель и подтверждает
- [ ] Тесты покрывают получение по роли, смену, валидацию несуществующей модели

## Phase 3: Переключение на модели из БД

**User stories**: 2, 7

### Что построить

Заменить использование `config.model` и `config.titleModel` на получение модели по роли из БД. При построении запроса использовать `context_size` модели для ограничения контекста. Удалить `OPENAI_MODEL` и `TITLE_MODEL` из конфигурации.

### Критерии приёмки

- [ ] Запрос к LLM использует модель из `model_roles` по роли `chat`
- [ ] Генерация заголовка использует модель по роли `title`
- [ ] Извлечение фактов использует модель по роли `facts`
- [ ] `context_size` модели учитывается при построении контекста запроса
- [ ] Переменные `OPENAI_MODEL` и `TITLE_MODEL` удалены из конфига
- [ ] Существующие тесты обновлены под новую схему получения модели

## Phase 4: Подсчёт и отображение стоимости

**User stories**: 1, 8

### Что построить

После получения ответа от API извлекать usage (input_tokens, output_tokens), вычислять стоимость по ценам модели из БД и выводить после каждого ответа. В debug-режиме показывать расширенные детали.

### Критерии приёмки

- [ ] После каждого ответа выводится стоимость в формате `💰 $0.0023 (1234 in / 567 out)`
- [ ] Стоимость корректно вычисляется по формуле из PRD
- [ ] В debug-режиме дополнительно показываются модель, цены, токены
- [ ] Стоимость показывается как в REPL-режиме, так и в режиме одиночного запроса
- [ ] Тесты покрывают расчёт стоимости и форматирование вывода
