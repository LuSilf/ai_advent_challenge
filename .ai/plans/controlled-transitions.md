# Plan: Контролируемые переходы состояний (День 15)

> Source PRD: `.ai/prd/controlled-transitions.md`

## Architectural decisions

- **Schema**: новая таблица `task_transitions` (id, task_id, from_phase, to_phase, triggered_by, created_at). `triggered_by` — enum-строка: `"llm"`, `"system"`, `"user"`.
- **Key models**: `TaskTransition` — новый доменный тип. `TaskPhase` — без изменений. `TaskStateMachine` — расширяется методами `getAllowedTransitions()`, `describeTransitions()`.
- **Паттерн маркеров**: JSON в HTML-комментариях `<!--task-update\n{...}\n-->` — без изменений формата, только ужесточение валидации.
- **Retry-контракт**: при невалидном переходе системное сообщение сохраняется в историю как `role: "user"` с префиксом `[Система]`, LLM получает его в контексте следующего запроса. Максимум 5 retry.
- **Паттерн паузы**: `paused` — внутреннее системное состояние, недоступное LLM. Управляется только `pauseAllActive()` и авто-resume.
- **Порт**: новый `TaskTransitionRepository` интерфейс + SQLite-адаптер.

## Phase 1: Аудит-лог переходов + расширение стейт-машины

**User stories**: 9, 4, 14

### What to build

Таблица `task_transitions` для хранения истории переходов. Репозиторий (порт + SQLite-адаптер) с методами записи и чтения. `TaskStateMachine` получает `getAllowedTransitions(from)` и `describeTransitions()`. `TaskService.transition()` логирует каждый успешный переход. `pauseAllActive()` и `cancelTask()` тоже логируют с соответствующим `triggered_by`. Команда `/task list` показывает количество переходов рядом с задачей. `/task` (статус) показывает последние переходы.

### Acceptance criteria

- [ ] Таблица `task_transitions` создаётся при инициализации БД
- [ ] Каждый успешный вызов `TaskService.transition()` создаёт запись в аудит-логе
- [ ] `pauseAllActive()` логирует переходы с `triggered_by: "system"`
- [ ] `cancelTask()` логирует с `triggered_by: "user"`
- [ ] `createTask()` логирует начальный переход `null → planning` с `triggered_by: "user"`
- [ ] `TaskStateMachine.getAllowedTransitions("planning")` возвращает `["execution", "cancelled"]` (без `paused`)
- [ ] `TaskStateMachine.describeTransitions()` возвращает человекочитаемый граф
- [ ] `/task` показывает историю переходов активной задачи
- [ ] Тесты: TaskStateMachine (новые методы), TaskTransitionRepository (CRUD), TaskService (логирование)

## Phase 2: Убираем ручные команды, пауза только автоматическая

**User stories**: 2, 7, 8

### What to build

Удаление команд `/task done`, `/task pause`, `/task switch` из REPL. Удаление `pauseTask()` и `resumeTask()` из публичного API TaskService. `paused` убирается из карты LLM-переходов в `TaskStateMachine` (остаётся только для внутреннего использования системой). Авто-resume при входе в сессию сохраняется: если одна paused задача — автоматически возобновляется, если несколько — показывается список. Обновление справки `/help`.

### Acceptance criteria

- [ ] `/task done` не существует — команда не распознаётся
- [ ] `/task pause` не существует
- [ ] `/task switch` не существует
- [ ] `TaskStateMachine.canTransition("planning", "paused")` возвращает `false` (LLM не может паузить)
- [ ] Внутренний метод паузы продолжает работать для `pauseAllActive()`
- [ ] При смене сессии все активные задачи паузятся автоматически
- [ ] При входе в сессию с одной paused задачей — она автоматически возобновляется
- [ ] `/help` не содержит удалённых команд
- [ ] Тесты: обновлённые тесты TaskStateMachine, TaskService, REPL

## Phase 3: Retry при невалидном переходе

**User stories**: 1, 3, 4, 5, 6

### What to build

В REPL после получения ответа LLM: парсинг маркера `<!--task-update-->` → валидация перехода → если невалиден → сохранение системного сообщения в историю (с графом переходов из `describeTransitions()`) → повторный запрос к LLM → повтор до 5 раз. Фазовые промпты обновляются: явно указывают допустимые переходы из текущей фазы и включают граф. При невалидном переходе спиннер показывает "Повторный запрос (попытка N/5)...".

### Acceptance criteria

- [ ] Невалидный переход в маркере вызывает повторный запрос к LLM
- [ ] Системное сообщение с графом переходов сохраняется в историю чата
- [ ] LLM получает это сообщение в контексте следующего запроса
- [ ] После валидного перехода на retry — переход применяется корректно
- [ ] После 5 неудачных попыток — последний ответ показывается без перехода, предупреждение в консоль
- [ ] Фазовые промпты содержат список допустимых переходов из текущей фазы
- [ ] Невалидный переход логируется в аудит как отклонённый (или не логируется — только успешные)
- [ ] Тесты: retry-цикл (мок LLM), граница 5 попыток, успешный retry на 2-3 попытке

## Phase 4: Спиннеры с описательными метками

**User stories**: 10, 11

### What to build

Обёртка над существующим `startSpinner()` для всех долгих операций в REPL. Каждый LLM-вызов сопровождается спиннером с описательной меткой: основной ответ, retry-попытки, reconciliation памяти, генерация заголовка сессии. Спиннер останавливается перед выводом результата.

### Acceptance criteria

- [ ] Основной LLM-вызов показывает "Генерация ответа..."
- [ ] Retry-попытки показывают "Повторный запрос (попытка N/5)..."
- [ ] Reconciliation памяти показывает "Обновление памяти..."
- [ ] Генерация заголовка показывает "Генерация заголовка..."
- [ ] Спиннер корректно останавливается перед выводом текста (нет артефактов)
- [ ] В streaming-режиме спиннер останавливается перед первым токеном
- [ ] Тесты: вызов startSpinner/stopSpinner в правильном порядке для каждого типа операции
