# Plan: Memory Reconciliation

> Source PRD: `.ai/prd/memory-reconciliation.md`

## Architectural decisions

- **Схема**: новая таблица `options (key TEXT PRIMARY KEY, value TEXT NOT NULL)` в SQLite
- **Формат ответа LLM**: JSON `{"updated_memory": "...", "changes_summary": "..."}` — свободный markdown в `updated_memory`
- **Перезапись памяти**: `writeMemoryFile(path, content)` — полная перезапись файла
- **Аккумулятор стоимости**: объект `{inputTokens, outputTokens}` с методами add/format/reset, живёт в рамках одного цикла
- **Дефолтные настройки**: `memory_interval = 5` (пар сообщений между предложениями рабочей памяти)
- **Формат вывода стоимости**: `💡 <статус>: $<cost> (<in> in / <out> out)`

## Фаза 1: Аккумулятор стоимости + writeMemoryFile

**User stories**: 5, 6, 13

### Что построить

Аккумулятор токенов, который собирает usage по нескольким LLM-запросам в рамках одного цикла работы с памятью и форматирует итоговую строку стоимости с произвольным статусом. Добавить в модуль памяти функцию полной перезаписи файла (вместо аппенда). Оба компонента с тестами.

### Критерии приёмки

- [ ] Аккумулятор накапливает input/output токены через метод add
- [ ] Аккумулятор форматирует итог: `💡 <статус>: $<cost> (<in> in / <out> out)`
- [ ] Аккумулятор сбрасывается через reset
- [ ] `writeMemoryFile` полностью перезаписывает файл (не аппендит)
- [ ] `writeMemoryFile` создаёт директории при необходимости
- [ ] Тесты на аккумулятор: накопление, форматирование, сброс
- [ ] Тесты на `writeMemoryFile`: перезапись, создание директорий

## Фаза 2: Модуль реконсиляции

**User stories**: 1, 2, 3, 5, 13

### Что построить

Функция реконсиляции: принимает текущее содержимое памяти и новый контент (диалог или текст), отправляет один LLM-запрос, возвращает структурированный результат с обновлённой памятью, описанием изменений и usage. Если текущая память пуста — упрощённый запрос (только извлечение фактов, без сравнения). Промпт инструктирует LLM не удалять существующее без причины, обновлять изменённое, добавлять новое. Тесты на парсинг JSON-ответа (валидный, невалидный, code block, «нет изменений»).

### Критерии приёмки

- [ ] Функция реконсиляции возвращает `{updated_memory, changes_summary, usage}`
- [ ] При пустой памяти отправляется упрощённый промпт (без сравнения)
- [ ] JSON-ответ LLM парсится корректно (с code block и без)
- [ ] Пустой `changes_summary` означает «нет изменений»
- [ ] При ошибке LLM — возвращается ошибка, не ломает основной поток
- [ ] Тесты на парсинг: валидный JSON, code block, невалидный, пустые изменения

## Фаза 3: Рабочая память через реконсиляцию

**User stories**: 1, 2, 3, 6, 14

### Что построить

Заменить текущий `suggestMemorySave` на пайплайн с реконсиляцией. После ответа ассистента запускается реконсиляция: LLM получает текущую рабочую память + последний обмен, возвращает дельту. Пользователю показывается только `changes_summary`. При подтверждении (`д`) — полная перезапись файла содержимым `updated_memory`. При `и` — редактирование `updated_memory` перед перезаписью. Стоимость всех memory-запросов за цикл выводится одной строкой с соответствующим статусом.

### Критерии приёмки

- [ ] Пользователю показывается дельта, а не полный текст
- [ ] `д` — перезапись файла памяти
- [ ] `н` — пропуск без записи
- [ ] `и` — редактирование обновлённой памяти перед записью
- [ ] Стоимость выводится после завершения: «Сохранено в рабочую память: стоимость», «Фактов не обнаружено: стоимость», «Факты отклонены: стоимость»
- [ ] При ошибке — сообщение, основной поток не блокируется

## Фаза 4: `/remember` через реконсиляцию

**User stories**: 4, 5, 6, 14

### Что построить

Команда `/remember текст` проходит через реконсиляцию: LLM получает текущую долговременную память + текст от пользователя, формирует обновлённую версию. Пользователю показывается дельта, д/н/и. При подтверждении — перезапись. Оптимизация: если долговременная память пуста — запись текста напрямую без LLM-запроса. Вывод стоимости после завершения.

### Критерии приёмки

- [ ] `/remember текст` при пустой памяти — запись без LLM, без стоимости
- [ ] `/remember текст` при существующей памяти — LLM-реконсиляция
- [ ] Показывается дельта, д/н/и
- [ ] При подтверждении — перезапись файла
- [ ] Вывод стоимости после завершения
- [ ] Тест: пустая память → прямая запись

## Фаза 5: Настройки в БД + интервал предложений

**User stories**: 7, 10, 11, 12

### Что построить

Таблица `options` в SQLite с CRUD-операциями. REPL-команды `/options` (показать все) и `/set ключ значение` (установить). Дефолтная опция `memory_interval = 5`. Счётчик пар сообщений в REPL — при достижении `memory_interval` запускается реконсиляция рабочей памяти. Счётчик сбрасывается после запуска.

### Критерии приёмки

- [ ] Таблица `options` создаётся при `initDb`
- [ ] `getOption(key)` / `setOption(key, value)` / `listOptions()` работают корректно
- [ ] Дефолтное значение `memory_interval = 5` предзаполняется
- [ ] `/options` показывает все настройки
- [ ] `/set memory_interval 3` меняет значение
- [ ] Реконсиляция рабочей памяти запускается каждые N пар сообщений
- [ ] Счётчик сбрасывается после запуска реконсиляции
- [ ] Тесты на CRUD настроек

## Фаза 6: Триггеры при смене сессии

**User stories**: 8, 9

### Что построить

Команды `/new`, `/switch`, `/exit` перед выполнением основного действия запускают реконсиляцию рабочей памяти, если с последнего запуска были новые сообщения. Выполнение команды блокируется до завершения реконсиляции и подтверждения пользователем (д/н/и). Только после этого выполняется само действие (создание/переключение сессии или выход).

### Критерии приёмки

- [ ] `/new` запускает реконсиляцию перед созданием сессии (если были сообщения)
- [ ] `/switch N` запускает реконсиляцию перед переключением
- [ ] `/exit` запускает реконсиляцию перед выходом
- [ ] Если сообщений не было — реконсиляция не запускается, команда выполняется сразу
- [ ] Реконсиляция блокирует выполнение команды до подтверждения пользователем
- [ ] Стоимость выводится после завершения
