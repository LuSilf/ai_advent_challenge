# Plan: День 22 — Первый RAG-запрос

> Source PRD: `.ai/prd/day-22-first-rag-query.md`

## Architectural decisions

Durable decisions that apply across all phases:

- **UI surface**: фича реализуется только в REPL, без отдельного web/API слоя.
- **Knowledge source**: используется существующий индекс документов из Day 21 по `system-design-primer`; индекс подготавливается отдельно и не строится автоматически в чате или в evaluation-команде.
- **RAG control**: управление режимом идёт через команды `/rag`, `/rag on`, `/rag off`, `/rag strategy <fixed|structural>`, `/rag topk <n>`.
- **Defaults**: по умолчанию `RAG = off`, retrieval strategy = `structural`, `topK = 5`.
- **Retrieval behavior**: жёсткий threshold по distance не используется; система берёт topK результатов и при отсутствии индекса или результатов делает явный fallback в non-RAG.
- **Grounding display**: источники, section, distance и сообщения о fallback печатает приложение отдельным техническим блоком, а не сама модель.
- **Configuration**: настройки RAG живут в существующем механизме options / runtime state и должны быть доступны из REPL.
- **Evaluation**: сравнение качества запускается отдельной командой, аналогично Day 21, и сохраняет markdown-отчёт в репозиторий.
- **Scoring**: оценка ответа строится гибридно — rules + judge — по шкале 0–3.
- **Judge model**: используется отдельная роль `judge` с fallback на роль `chat`.
- **Expected sources**: проверка groundedness опирается в первую очередь на `section`, а путь к файлу показывается в отчёте как вспомогательная информация.

## Phase 1: Minimal REPL RAG path

**User stories**: 1, 2, 3, 7, 8, 12, 14

### What to build

Собрать минимальный, но полный сквозной путь для RAG в REPL. Пользователь должен иметь возможность включить RAG и отправить вопрос, после чего система выполнит retrieval по уже существующему индексу, соберёт контекст и отправит вопрос в LLM с retrieval-данными. Если индекс недоступен или retrieval ничего не дал, чат не должен ломаться: система явно сообщает о fallback и продолжает обычный non-RAG запрос.

### Acceptance criteria

- [ ] Пользователь может включить и выключить RAG из REPL.
- [ ] При включённом RAG вопрос проходит через retrieval и попадает в LLM с retrieval-контекстом.
- [ ] При отсутствии индекса или результатов retrieval система даёт явный fallback в non-RAG без падения.
- [ ] Поведение покрыто тестами на orchestration и интеграцию с чатом.

## Phase 2: RAG status and tuning commands

**User stories**: 4, 5, 6, 15

### What to build

Довести управление RAG до удобного пользовательского состояния. В REPL должна появиться статус-строка с текущим состоянием RAG и активными параметрами. Пользователь должен уметь просматривать текущую конфигурацию, менять retrieval strategy и topK, а изменения должны использоваться последующими запросами без перезапуска REPL.

### Acceptance criteria

- [ ] В REPL отображается статус-строка с состоянием RAG и активными retrieval-настройками.
- [ ] Команда просмотра статуса показывает текущие значения включённости, strategy и topK.
- [ ] Команды изменения strategy и topK валидируют ввод и меняют поведение последующих запросов.
- [ ] Поведение команд и настроек покрыто тестами presentation-слоя.

## Phase 3: Grounding techblock for chat answers

**User stories**: 9, 10, 11, 13

### What to build

Добавить прозрачный технический блок вывода для RAG-ответов. После retrieval приложение должно отдельно отображать, какие чанки были найдены, из каких источников и секций они пришли, а также какие у них distance. При fallback должен печататься явный техблок, объясняющий, почему ответ был дан без RAG. При этом основной текст модели должен оставаться чистым и удобочитаемым.

### Acceptance criteria

- [ ] Для RAG-ответа приложение печатает отдельный техблок с retrieved chunks, source, section и distance.
- [ ] Для fallback-сценария приложение печатает отдельное понятное сообщение о работе без RAG.
- [ ] Основной текст модели не смешивается с техническими retrieval-метаданными.
- [ ] Формат техблока покрыт тестами и пригоден для последующего использования в отчёте.

## Phase 4: Day 22 evaluation runner and control-question dataset

**User stories**: 16, 17, 18, 19, 20, 21, 22, 23, 24

### What to build

Создать отдельную команду оценки Day 22 и набор контрольных вопросов для неё. Команда должна брать базовый набор Day 21, расширенный ожиданиями для финального ответа, и для каждого вопроса запускать два прогона: без RAG и с RAG. Результат должен фиксировать сами ответы, retrieval-метаданные RAG-прогона и стоимость обоих режимов, а затем сохранять markdown-отчёт, пригодный для ручного сравнения.

### Acceptance criteria

- [ ] В проекте есть отдельная команда оценки Day 22, которая требует заранее подготовленный индекс.
- [ ] Набор контрольных вопросов содержит формулировку вопроса, ожидание ответа и ожидаемые источники по section.
- [ ] Для каждого вопроса команда сохраняет ответ без RAG, ответ с RAG, retrieval-метаданные и стоимость обоих режимов.
- [ ] Команда сохраняет markdown-отчёт для ручного анализа качества.

## Phase 5: Rules-based scoring and report verdicts

**User stories**: 19, 20, 25, 29

### What to build

Поверх базового evaluation-runner добавить воспроизводимую deterministic scoring-систему. Для каждого ответа нужно оценивать наличие обязательных смыслов, желательных смыслов и использование ожидаемых section в RAG-режиме. Результаты rule-based проверки должны попадать в итоговый отчёт вместе с краткими verdicts по каждому вопросу.

### Acceptance criteria

- [ ] Для контрольных вопросов поддерживаются поля обязательных и желательных смыслов.
- [ ] Evaluator считает rule-based score для non-RAG и RAG ответа.
- [ ] Проверка ожидаемых источников в RAG-режиме учитывает section retrieved-чанков.
- [ ] Markdown-отчёт содержит rule-based оценки и краткие verdicts по каждому вопросу.

## Phase 6: Judge scoring and final comparison summary

**User stories**: 26, 27, 28, 29, 30

### What to build

Добавить judge-слой в evaluation pipeline. Для каждого ответа должна запускаться отдельная judge-оценка, которая выставляет score по шкале 0–3 на основе ожидания, ответа и, при необходимости, retrieval-данных. В отчёте должна появиться финальная сводка, сравнивающая non-RAG и RAG по качеству, groundedness и стоимости, чтобы можно было сделать итоговый вывод по упражнению Day 22.

### Acceptance criteria

- [ ] В системе поддерживается роль judge с fallback на chat.
- [ ] Evaluator получает judge-score 0–3 для non-RAG и RAG ответа.
- [ ] Итоговый markdown-отчёт показывает сравнительную сводку по quality score и cost для двух режимов.
- [ ] Полный evaluation pipeline покрыт тестами orchestration-уровня с подменённым LLM-клиентом.
