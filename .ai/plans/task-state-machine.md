# Plan: Task State Machine

> Source PRD: `.ai/prd/task-state-machine.md`

## Архитектурные решения

- **Модель данных**: `Task` — новая доменная сущность с полями `id`, `sessionId`, `title`, `phase`, `previousPhase`, `currentStep`, `expectedAction`, `summary`, `createdAt`, `updatedAt`
- **Фазы**: `planning`, `execution`, `validation`, `done`, `paused`, `cancelled`
- **Схема БД**: таблица `tasks` с FK на `sessions(id) ON DELETE CASCADE`. Миграция обратно совместима — существующие сессии без задач работают как раньше
- **Порт**: `TaskRepository` — интерфейс в `domain/ports/`, SQLite-адаптер в `storage/sqlite/`
- **Маркеры LLM**: HTML-комментарии `<!--task-update ... -->` и `<!--task-detect ... -->` — парсятся ChatService, удаляются из вывода пользователю
- **REPL-команды**: `/task`, `/task create`, `/task list`, `/task pause`, `/task cancel`, `/task switch`
- **Допустимые переходы**:
  ```
  planning   → execution, paused, cancelled
  execution  → validation, planning, paused, cancelled
  validation → done, execution, paused, cancelled
  paused     → {previousPhase}
  done       → (терминальное)
  cancelled  → (терминальное)
  ```

## Phase 1: Ядро State Machine + персистентность

**User stories**: 6, 20

### Что построить

Сквозной слайс от доменной модели до БД. Определить тип `Task` в доменных моделях. Реализовать `TaskStateMachine` — чистый модуль валидации переходов между фазами (без зависимостей). Определить порт `TaskRepository` и его SQLite-адаптер. Добавить миграцию таблицы `tasks` в `db.ts`. Написать тесты для всех трёх компонентов.

### Критерии приёмки

- [ ] Тип `Task` определён в `domain/models`
- [ ] `TaskStateMachine.canTransition(from, to)` корректно валидирует все допустимые и недопустимые переходы
- [ ] `TaskStateMachine` корректно обрабатывает `paused` → `previousPhase`
- [ ] Терминальные состояния (`done`, `cancelled`) не имеют исходящих переходов
- [ ] Порт `TaskRepository` определён с методами: `create`, `findById`, `findBySessionId`, `findActive`, `update`
- [ ] SQLite-адаптер реализует порт, таблица `tasks` создаётся при инициализации БД
- [ ] Миграция обратно совместима — существующие БД не ломаются
- [ ] Юнит-тесты TaskStateMachine покрывают все переходы
- [ ] Интеграционные тесты TaskRepository покрывают CRUD и `findActive`
- [ ] Все тесты проходят, проект собирается

## Phase 2: TaskService + базовые REPL-команды

**User stories**: 1, 4, 14, 17, 22

### Что построить

Сквозной слайс от пользовательской команды до БД и обратно. Реализовать `TaskService` с базовой бизнес-логикой: создание задачи (в фазе `planning`), получение активной задачи, получение списка задач сессии. При создании новой задачи автоматически паузить предыдущую активную. Добавить REPL-команды `/task create "описание"`, `/task` (показать текущую), `/task list`. Подключить `TaskService` в граф зависимостей REPL.

### Критерии приёмки

- [ ] `/task create "описание"` создаёт задачу в фазе `planning` и показывает подтверждение
- [ ] При создании новой задачи предыдущая активная автоматически ставится на паузу
- [ ] `/task` показывает текущую активную задачу: title, phase, currentStep, expectedAction, summary
- [ ] `/task` без активной задачи показывает сообщение "Нет активной задачи"
- [ ] `/task list` показывает все задачи сессии с их фазами
- [ ] Завершённые задачи (`done`) остаются в списке
- [ ] Юнит-тесты TaskService покрывают создание и автопаузу
- [ ] Тесты REPL-команд покрывают вызовы TaskService
- [ ] Все тесты проходят, проект собирается

## Phase 3: Переходы фаз и управление задачами

**User stories**: 5, 7, 8, 9, 15, 16

### Что построить

Сквозной слайс управления жизненным циклом задачи через REPL. Добавить в `TaskService` методы: `transition` (с валидацией через TaskStateMachine), `pauseTask`, `resumeTask`, `cancelTask`. Добавить REPL-команды `/task pause`, `/task cancel`, `/task switch` (показывает список и переключает). При resume восстанавливать `previousPhase`.

### Критерии приёмки

- [ ] `/task pause` ставит активную задачу на паузу, сохраняет `previousPhase`
- [ ] `/task switch` показывает список paused-задач и позволяет выбрать
- [ ] При switch выбранная задача resume-ится в `previousPhase`, текущая активная ставится на паузу
- [ ] `/task cancel` переводит активную задачу в `cancelled`
- [ ] `transition` отклоняет невалидные переходы (например `planning → done`)
- [ ] Откат `validation → execution` работает корректно
- [ ] Откат `execution → planning` работает корректно
- [ ] Юнит-тесты TaskService покрывают все переходы, паузу, resume, cancel
- [ ] Все тесты проходят, проект собирается

## Phase 4: Фазовые промпты + интеграция с ChatService

**User stories**: 3, 18, 19

### Что построить

Сквозной слайс от ввода пользователя до изменения фазы задачи через LLM. При наличии активной задачи ChatService добавляет фазовый промпт в системное сообщение (planning/execution/validation). LLM включает маркер `<!--task-update-->` в ответ. ChatService парсит маркер, валидирует переход через TaskStateMachine, применяет изменения (phase, currentStep, expectedAction, summary), удаляет маркер из вывода пользователю. Обновление `currentStep` и `expectedAction` возможно и без перехода фазы (transition = null).

### Критерии приёмки

- [ ] При активной задаче в фазе `planning` — LLM получает промпт планирования
- [ ] При активной задаче в фазе `execution` — LLM получает промпт выполнения
- [ ] При активной задаче в фазе `validation` — LLM получает промпт проверки
- [ ] Маркер `<!--task-update-->` парсится из ответа LLM
- [ ] Валидный переход применяется: фаза, шаг, ожидаемое действие, резюме обновляются
- [ ] Невалидный переход в маркере отклоняется (задача не меняется, пользователь видит предупреждение)
- [ ] Маркер удаляется из текста ответа, показываемого пользователю
- [ ] Обновление шага без перехода (transition: null) работает корректно
- [ ] Юнит-тесты ChatService покрывают добавление промптов и парсинг маркеров
- [ ] Все тесты проходят, проект собирается

## Phase 5: Автодетект задач

**User stories**: 2

### Что построить

Сквозной слайс автоматического обнаружения новых задач. Когда нет активной задачи в сессии, ChatService добавляет промпт автодетекта. LLM включает маркер `<!--task-detect-->` если считает, что пользователь ставит задачу. ChatService парсит маркер и запрашивает у пользователя подтверждение: "Похоже, вы ставите задачу: X. Создать? (y/n)". При подтверждении — создаёт задачу через TaskService.

### Критерии приёмки

- [ ] Без активной задачи LLM получает промпт автодетекта
- [ ] Маркер `<!--task-detect-->` парсится из ответа LLM
- [ ] Пользователю показывается подтверждение с предложенным названием задачи
- [ ] При ответе "y" — задача создаётся в фазе `planning`
- [ ] При ответе "n" — задача не создаётся, диалог продолжается
- [ ] Маркер удаляется из текста ответа
- [ ] При наличии активной задачи промпт автодетекта НЕ добавляется
- [ ] Юнит-тесты покрывают парсинг маркера и ветвление по подтверждению
- [ ] Все тесты проходят, проект собирается

## Phase 6: Восстановление сессии

**User stories**: 10, 11, 12, 13, 21

### Что построить

Сквозной слайс сохранения и восстановления контекста задач. При выходе из REPL (`/exit`, Ctrl+D) или переключении сессии (`/switch`) — вызывать `TaskService.pauseAllActive(sessionId)`. При входе в сессию (запуск REPL, `/switch`) — проверять наличие задач, показывать резюме из БД (не генерировать через LLM). Если есть единственная paused задача — автоматически resume-ить её. Если несколько — показать список и предложить выбрать.

### Критерии приёмки

- [ ] При `/exit` все активные задачи текущей сессии ставятся на паузу
- [ ] При `/switch` все активные задачи покидаемой сессии ставятся на паузу
- [ ] При входе в сессию с одной paused задачей — она автоматически resume-ится, показывается резюме
- [ ] При входе в сессию с несколькими paused задачами — показывается список с резюме
- [ ] Резюме берётся из БД (поле `summary`), а не генерируется LLM
- [ ] При входе в сессию без задач — поведение как раньше (без изменений)
- [ ] Тесты покрывают автопаузу и восстановление
- [ ] Все тесты проходят, проект собирается
