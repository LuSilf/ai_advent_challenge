# PRD: Стратегии управления контекстом

## Problem Statement

CLI-агент отправляет в LLM всю историю сообщений сессии без какого-либо управления контекстом. При длинных диалогах это приводит к неконтролируемому расходу токенов, потере фокуса модели на важных деталях, и невозможности экспериментировать с разными подходами к одному и тому же диалогу. Пользователь не может выбрать, как именно формировать контекст запроса, и не может сравнить поведение агента при разных стратегиях.

## Solution

Реализовать 4 стратегии управления контекстом с возможностью переключения между ними:

- **Full** (по умолчанию) — отправляет всю историю сессии без ограничений
- **Sliding Window** — отправляет только последние N сообщений, остальное отбрасывает
- **Sticky Facts** — извлекает ключевые факты из диалога через отдельный LLM-запрос, отправляет facts + последние N сообщений
- **Branching** — позволяет создавать checkpoint и ветвить диалог от него, продолжая в каждой ветке независимо с любой стратегией

Переключение стратегий возможно через переменную окружения `CONTEXT_STRATEGY` и через REPL-команду `/strategy`. Стратегия привязана к сессии и сохраняется в БД.

## User Stories

1. As a пользователь, I want переключать стратегию контекста через env-переменную `CONTEXT_STRATEGY`, so that я могу задать стратегию по умолчанию при запуске.
2. As a пользователь, I want переключать стратегию через REPL-команду `/strategy [name]`, so that я могу менять стратегию на лету внутри сессии.
3. As a пользователь, I want видеть текущую стратегию при вызове `/strategy` без аргументов, so that я знаю, какая стратегия сейчас активна.
4. As a пользователь, I want чтобы стратегия сохранялась в БД для каждой сессии, so that при переключении между сессиями стратегия восстанавливалась.
5. As a пользователь, I want использовать стратегию "full", so that вся история диалога отправлялась в LLM без ограничений.
6. As a пользователь, I want использовать стратегию "sliding", so that в контекст попадали только последние N сообщений, экономя токены.
7. As a пользователь, I want чтобы размер окна sliding window управлялся настройкой `HISTORY_LIMIT`, so that я мог контролировать глубину окна.
8. As a пользователь, I want использовать стратегию "facts", so that агент извлекал ключевые факты из диалога и отправлял их вместе с последними N сообщениями.
9. As a пользователь, I want чтобы факты извлекались автоматически после каждого моего сообщения через отдельный LLM-запрос, so that блок фактов всегда был актуален.
10. As a пользователь, I want чтобы факты хранились в SQLite и были привязаны к сессии, so that они сохранялись между перезапусками.
11. As a пользователь, I want просматривать текущие факты командой `/facts`, so that я мог видеть, что агент "запомнил".
12. As a пользователь, I want чтобы факты включались в запрос как отдельный блок в системном промпте или в начале истории, so that модель видела ключевую информацию перед последними сообщениями.
13. As a пользователь, I want чтобы стратегия "facts" использовала тот же `HISTORY_LIMIT` для размера окна последних сообщений, so that не нужна отдельная настройка.
14. As a пользователь, I want создать checkpoint в диалоге командой `/checkpoint`, so that я мог потом создать ветки от этой точки.
15. As a пользователь, I want создать ветку от checkpoint командой `/branch [name]`, so that я мог продолжить диалог в новом направлении.
16. As a пользователь, I want видеть список веток командой `/branches`, so that я знал, какие ветки существуют.
17. As a пользователь, I want переключаться между ветками командой `/switch-branch N`, so that я мог работать в разных ветках.
18. As a пользователь, I want чтобы при создании ветки сообщения до checkpoint копировались в новую сессию, so that каждая ветка была независимой.
19. As a пользователь, I want задавать разные стратегии контекста в разных ветках, so that я мог сравнить поведение агента на одном и том же диалоге с разными стратегиями.
20. As a пользователь, I want чтобы новая сессия по умолчанию использовала стратегию из env-переменной или "full", so that было предсказуемое поведение без дополнительной настройки.
21. As a пользователь, I want видеть в debug-логах, какая стратегия используется и сколько сообщений/фактов отправляется, so that я мог отлаживать и сравнивать стратегии.

## Implementation Decisions

### Модули

**1. Context Strategy (ядро)**
- Интерфейс `ContextStrategy` с методом `buildMessages(sessionId, newPrompt) → ChatMessage[]`
- Метод опционально может возвращать дополнительный системный контекст (для facts)
- 4 реализации: `FullStrategy`, `SlidingWindowStrategy`, `StickyFactsStrategy`
- `BranchingStrategy` не является отдельной стратегией контекста — branching это механизм управления сессиями, а стратегия контекста задаётся per-session
- Фабрика `createStrategy(name) → ContextStrategy` для создания стратегии по имени

**2. Facts (извлечение и хранение)**
- Новая таблица `facts` в SQLite: `session_id`, `key`, `value`, `updated_at`
- Извлечение фактов через отдельный LLM-запрос после каждого сообщения пользователя
- Промпт для извлечения фактов: принимает текущие факты + последнее сообщение пользователя + ответ ассистента, возвращает обновлённый JSON с фактами
- Факты включаются в системный промпт как блок "Известные факты о диалоге:" перед основным промптом
- DB-функции: `getFacts(sessionId)`, `upsertFacts(sessionId, facts)`, `clearFacts(sessionId)`

**3. Branching (ветки диалога)**
- Новые поля в таблице `sessions`: `parent_session_id INTEGER`, `branch_point_message_id INTEGER`, `context_strategy TEXT DEFAULT 'full'`
- При `/checkpoint` — запоминается ID последнего сообщения текущей сессии (хранится in-memory в REPL или в отдельной таблице)
- При `/branch [name]` — создаётся новая сессия с `parent_session_id` = текущая сессия, `branch_point_message_id` = checkpoint, копируются все сообщения до checkpoint включительно
- `/branches` — показывает все сессии с `parent_session_id` = текущая сессия (или общий родитель)
- `/switch-branch N` — переключает на указанную ветку (по сути `/switch` на сессию-ветку)

**4. REPL-команды**
- `/strategy [name]` — показать текущую / переключить стратегию (full, sliding, facts)
- `/facts` — показать текущие факты сессии
- `/checkpoint` — создать точку ветвления
- `/branch [name]` — создать ветку от последнего checkpoint
- `/branches` — показать все ветки текущей сессии

**5. Config**
- Новая переменная `CONTEXT_STRATEGY` (default: `full`), допустимые значения: `full`, `sliding`, `facts`
- Добавляется в `AppConfig` как `contextStrategy`

**6. Изменения в основном flow**
- В `cli.ts` и `repl.ts`: вместо прямого вызова `getMessages()` — вызов `strategy.buildMessages()`
- После получения ответа ассистента в стратегии "facts" — дополнительный LLM-запрос для обновления фактов
- В debug-логах: вывод имени стратегии, количества сообщений в контексте, количества фактов (если есть)

### Схема БД (миграции)

Таблица `sessions` — новые поля:
- `context_strategy TEXT DEFAULT 'full'`
- `parent_session_id INTEGER REFERENCES sessions(id)`
- `branch_point_message_id INTEGER REFERENCES messages(id)`

Новая таблица `facts`:
```
facts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id INTEGER NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  key TEXT NOT NULL,
  value TEXT NOT NULL,
  updated_at TEXT DEFAULT (datetime('now')),
  UNIQUE(session_id, key)
)
```

Новая таблица `checkpoints`:
```
checkpoints (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id INTEGER NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
  message_id INTEGER NOT NULL REFERENCES messages(id),
  created_at TEXT DEFAULT (datetime('now'))
)
```

## Testing Decisions

Хороший тест проверяет внешнее поведение модуля через его публичный интерфейс, а не внутренние детали реализации. Тесты должны быть устойчивы к рефакторингу — если поведение не изменилось, тесты не должны ломаться.

Существующие тесты (`db.test.ts`, `config.test.ts`, `request.test.ts`) служат примером стиля: используется `bun:test`, in-memory SQLite для БД-тестов, мокирование env-переменных для config-тестов.

### Что тестируем

**Модуль 1: Context Strategy**
- `FullStrategy.buildMessages()` — возвращает все сообщения сессии
- `SlidingWindowStrategy.buildMessages()` — возвращает только последние N сообщений
- `StickyFactsStrategy.buildMessages()` — возвращает facts-блок + последние N сообщений
- Фабрика `createStrategy()` — корректно создаёт стратегию по имени, ошибка при неизвестном имени

**Модуль 2: Facts**
- DB-функции: `upsertFacts`, `getFacts`, `clearFacts` — CRUD операции с фактами
- Извлечение фактов: промпт формируется корректно, результат парсится и сохраняется (LLM-вызов мокируется)

**Модуль 3: Branching**
- `createBranch()` — создаёт сессию с правильными parent/branch_point полями, копирует сообщения
- `listBranches()` — возвращает ветки для данной сессии
- Checkpoint — сохраняется и используется при ветвлении

**Модуль 4: Config**
- Парсинг `CONTEXT_STRATEGY` из env
- Валидация допустимых значений
- Default значение "full"

## Out of Scope

- **Summary-стратегия** — автоматическое суммирование старых сообщений (явно исключено в задании)
- **Автоматический выбор стратегии** — агент не выбирает стратегию сам, только пользователь
- **Merge веток** — объединение веток обратно в одну не поддерживается
- **Удаление отдельных фактов** — только полная очистка через `/clear` или смену стратегии
- **Лимит на количество фактов** — не ограничиваем количество key-value пар
- **Вложенные ветки** — ветки от веток формально возможны (через checkpoint в ветке), но не являются приоритетом

## Further Notes

- Стратегия "facts" требует дополнительный LLM-запрос после каждого обмена сообщениями, что увеличивает расход токенов и латентность. Для извлечения фактов используется та же модель (`titleModel` или основная).
- При ручном тестировании рекомендуется прогнать сценарий "собираем ТЗ за 10-15 сообщений" на каждой стратегии и сравнить: качество ответов, стабильность (не теряет ли важные детали), расход токенов (из debug-логов), удобство для пользователя.
- `HISTORY_LIMIT` в стратегии "full" игнорируется (отправляется вся история). В стратегиях "sliding" и "facts" определяет размер окна.
