# PRD: Управление контекстом — сжатие истории чата

## Problem Statement

При длинных сессиях чата вся история сообщений отправляется в LLM-запрос целиком. Это приводит к:
- Растущему расходу токенов (и денег) с каждым сообщением
- Потенциальному превышению контекстного окна модели
- Оплате за повторную передачу одних и тех же старых сообщений при каждом запросе

Пользователю нужен механизм, который автоматически сжимает старую часть истории в краткое summary, сохраняя контекст разговора и экономя токены.

## Solution

Реализовать автоматическое сжатие истории чата:

1. **Последние N сообщений** (по умолчанию 10) хранятся и отправляются "как есть"
2. **Старые сообщения** (за горизонтом N) автоматически заменяются кумулятивным summary
3. **Summary** генерируется той же LLM-моделью и хранится в отдельной таблице SQLite (одна запись на сессию, обновляется при каждом сжатии)
4. **В запрос подставляется**: системный промпт + summary (как user-сообщение) + последние N сообщений
5. **После каждого ответа** выводится статистика: input/output токены и стоимость
6. **Команда `/benchmark`** позволяет сравнить ответ с полной историей и со сжатой в двух колонках

## User Stories

1. As a пользователь чата, I want старые сообщения автоматически сжимались в summary, so that я экономлю токены и деньги при длинных сессиях
2. As a пользователь чата, I want последние N сообщений сохранялись без изменений, so that контекст ближайшего разговора не терялся
3. As a пользователь чата, I want видеть статистику токенов после каждого ответа, so that я понимал сколько трачу
4. As a пользователь чата, I want видеть стоимость запроса в долларах, so that я мог контролировать расходы
5. As a пользователь чата, I want настраивать цену за токены через переменные окружения, so that цены соответствовали моей модели
6. As a пользователь чата, I want summary обновлялся автоматически при накоплении сообщений за горизонтом, so that мне не нужно думать о сжатии
7. As a пользователь чата, I want кумулятивный summary (один на сессию, растущий), so that вся старая история была сжата в один компактный блок
8. As a пользователь чата, I want посмотреть текущий summary командой `/summary`, so that я понимал что "помнит" система
9. As a пользователь чата, I want сравнить ответ с и без сжатия командой `/benchmark`, so that я видел разницу в качестве и расходе токенов
10. As a пользователь чата, I want результат бенчмарка выводился в двух колонках, so that сравнение было наглядным
11. As a пользователь чата, I want в бенчмарке видеть расход токенов и цену для обоих вариантов, so that я мог оценить экономию
12. As a пользователь чата, I want настраивать количество "живых" сообщений (N) через env-переменную, so that я мог подобрать баланс между контекстом и экономией
13. As a пользователь чата, I want summary подставлялся как user-сообщение перед живыми сообщениями, so that модель получала контекст в правильном порядке
14. As a пользователь чата, I want summary генерировался той же моделью что и ответы, so that не нужно настраивать отдельную модель
15. As a пользователь чата, I want статистика токенов выводилась всегда (не только в debug-режиме), so that я всегда видел расходы

## Implementation Decisions

### Модули

**1. Summarizer** — ядро сжатия
- Принимает текущий summary (или пустую строку) + блок сообщений, которые "уходят за горизонт"
- Отправляет запрос к LLM с промптом для генерации обновлённого summary
- Возвращает новый кумулятивный summary
- Промпт для суммаризации — специализированный (не пользовательский системный промпт), нацеленный на сжатое, фактологическое резюме

**2. Таблица `summaries` в SQLite**
- Поля: `id`, `session_id` (уникальный, один summary на сессию), `content` (текст summary), `message_count` (сколько сообщений было сжато), `updated_at`
- CRUD-операции: `getSummary(sessionId)`, `upsertSummary(sessionId, content, messageCount)`
- При удалении сессии — каскадное удаление summary

**3. Context Builder** — сборка контекста для запроса
- Определяет, какие сообщения отправить "как есть" (последние N)
- Определяет, какие сообщения нужно сжать (все до последних N)
- Если есть несжатые сообщения за горизонтом — вызывает Summarizer для обновления summary
- Формирует итоговый массив: `[{role: "user", content: summary}] + последние N сообщений`

**4. Token Stats** — статистика токенов и стоимости
- Извлекает usage из ответа API (input_tokens, output_tokens)
- Рассчитывает стоимость на основе цен из конфигурации
- Выводит после каждого ответа: input tokens, output tokens, total cost
- Дефолтные цены: input $0.05/1M, output $0.40/1M (gpt-5-nano на OpenRouter)

**5. Benchmark** — команда `/benchmark`
- Пользователь вводит промпт
- Система отправляет два запроса: один с полной историей, другой со сжатой
- Результаты выводятся в двух колонках: ответ, токены, цена
- Запросы можно делать параллельно

### Конфигурация (env-переменные)

- `CONTEXT_TAIL_SIZE` — количество "живых" сообщений (по умолчанию 10)
- `TOKEN_PRICE_INPUT` — цена за 1M input-токенов в USD (по умолчанию 0.05)
- `TOKEN_PRICE_OUTPUT` — цена за 1M output-токенов в USD (по умолчанию 0.40)

### Формат вывода статистики

После каждого ответа:
```
📊 Tokens: 1234 in / 567 out | Cost: $0.0029
```

### Формат вывода бенчмарка

```
┌─────────────────────────────┬─────────────────────────────┐
│        Со сжатием           │        Без сжатия           │
├─────────────────────────────┼─────────────────────────────┤
│ [ответ модели]              │ [ответ модели]              │
├─────────────────────────────┼─────────────────────────────┤
│ Tokens: 234 in / 567 out   │ Tokens: 1234 in / 567 out   │
│ Cost: $0.0012               │ Cost: $0.0029               │
│ Messages sent: 10 + summary │ Messages sent: 50           │
└─────────────────────────────┴─────────────────────────────┘
```

### Порядок формирования контекста

1. Загрузить все сообщения сессии
2. Если сообщений > N:
   a. Определить "старые" — всё кроме последних N
   b. Загрузить текущий summary из БД
   c. Определить, сколько из "старых" ещё не вошли в summary (по `message_count`)
   d. Если есть несжатые — вызвать Summarizer, обновить summary в БД
3. Сформировать input: `[summary как user-msg]` + последние N сообщений
4. Если сообщений <= N — отправить как есть, без summary

## Testing Decisions

Тесты должны проверять **внешнее поведение** модулей через их публичные интерфейсы, а не детали реализации. Стиль — аналогичный существующим тестам в проекте (`*.test.ts`, `bun:test`).

### Тестируемые модули

**1. Summarizer**
- Генерация summary из блока сообщений (мок API-вызова)
- Кумулятивное обновление: старый summary + новые сообщения → обновлённый summary
- Обработка пустого начального summary
- Обработка ошибок API

**2. Таблица summaries в БД**
- Создание summary для сессии
- Обновление существующего summary (upsert)
- Получение summary по session_id
- Каскадное удаление при удалении сессии
- Отсутствие summary для новой сессии

**3. Context Builder**
- Сообщений <= N → возвращает все как есть, без summary
- Сообщений > N → возвращает summary + последние N
- Корректное определение несжатых сообщений
- Вызов Summarizer только при наличии несжатых сообщений

**4. Token Stats**
- Расчёт стоимости по дефолтным ценам
- Расчёт стоимости по пользовательским ценам
- Форматирование вывода

**5. Benchmark**
- Формирование двух запросов (с и без сжатия)
- Форматирование вывода в две колонки
- Корректное отображение статистики для обоих вариантов

### Подход к мокам
- API-вызовы к LLM — мокаются (и для summarizer, и для benchmark)
- SQLite — используется реальная in-memory БД (как в существующих тестах)

## Out of Scope

- Ручное включение/выключение сжатия через env или команду (сжатие всегда активно)
- Выбор отдельной модели для суммаризации (используется та же модель)
- Сжатие на основе количества токенов (сжимаем по количеству сообщений)
- Несколько summary на сессию (только кумулятивный, один на сессию)
- Автоматический выбор оптимального N
- Экспорт/импорт summary
- Визуальные графики расхода токенов

## Further Notes

- Summary генерируется **до** отправки основного запроса, поэтому добавляет latency при первом сжатии. В последующих запросах сжатие происходит инкрементально (только новые "ушедшие" сообщения), что минимизирует задержку.
- Промпт для суммаризации должен быть на русском и просить фактологическое, сжатое резюме без потери ключевых деталей.
- Цены по умолчанию ($0.05/1M input, $0.40/1M output) соответствуют модели `openai/gpt-5-nano` на OpenRouter.
- Статистика токенов выводится всегда, не только в debug-режиме.
