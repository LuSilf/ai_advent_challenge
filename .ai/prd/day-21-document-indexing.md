# PRD: День 21 — Индексация документов

## Problem Statement

У агента нет способа превратить большой внешний документ в поисковую базу знаний для будущего RAG. Нельзя взять markdown-файл на 30–40 страниц, разбить его на чанки с метаданными, посчитать эмбеддинги и сохранить индекс, к которому потом можно ходить с запросами «найди релевантные куски». Без этого невозможно перейти к retrieval-augmented generation на дне 22 — LLM будет отвечать только по тому, что влезло в контекст одного промпта.

Вторая половина проблемы — выбор стратегии разбиения. Существует два базовых подхода (резать по фиксированному размеру или по структуре документа), и заранее непонятно, какой из них даёт лучшее качество retrieval на реальных запросах. Нужен воспроизводимый эксперимент, который честно сравнит обе стратегии на одном и том же корпусе.

## Solution

Пайплайн индексации документов, встроенный в существующую гекс-архитектуру проекта. Компоненты:

1. **Chunker** — порт с двумя реализациями:
   - `FixedSizeChunker` — режет текст на окна фиксированного размера в символах с настраиваемым overlap.
   - `StructuralMarkdownChunker` — парсит markdown и режет по заголовкам второго уровня (`##`); если секция получается больше порога, дорезает по `###`. Собирает breadcrumb заголовков для каждого чанка.
2. **Embedder** — порт, реализован через локальный Ollama (`bge-m3`, 1024 dim). Принимает массив строк, возвращает массив векторов.
3. **VectorIndex** — порт, реализован через SQLite + расширение `sqlite-vec`. Хранит чанки с метаданными в обычной таблице и векторы в `vec0` виртуальной таблице, связанной по id. Умеет `upsert(chunks[])` и `search(queryVector, k, filter)` с фильтром по стратегии.
4. **IndexingService** — доменный сервис-оркестратор: читает файл → вызывает чанкер → вызывает эмбеддер → сохраняет в индекс. Используется один раз за прогон для каждой стратегии.
5. **Две CLI-команды**:
   - `index <file> --strategy <fixed|structural>` — прогоняет пайплайн для одной стратегии и печатает статистику (количество чанков, средний размер, время).
   - `eval` — читает 10 заранее заготовленных запросов с ground truth из `scripts/day21/test-queries.json`, гоняет retrieval для обеих стратегий, считает Recall@3 и MRR, печатает markdown-табличку сравнения и сохраняет её в `scripts/day21/report.md`.
6. **Настройки индексации хранятся в таблице `options`** (существующая KV-таблица) — размеры чанков, overlap, провайдер/модель эмбеддингов, URL Ollama. Код имеет разумные фолбэки, если ключа в БД нет.
7. **Тестовый корпус** — `README.md` из `donnemartin/system-design-primer` (CC BY 4.0), закоммичен в `scripts/day21/data/` вместе с файлом атрибуции.
8. **Ground truth** — 10 вручную составленных запросов по известным разделам документа, с ожидаемыми заголовками секций и ключевыми словами. Файл `scripts/day21/test-queries.json`.
9. **Отчёт** — `scripts/day21/report.md` с табличкой по двум стратегиям (Recall@3, MRR, количество чанков, средний размер, время индексации) и несколькими примерами запросов с топ-3 результатами от каждой стратегии для качественной проверки.

Пользователь запускает `bun run src/main.ts index scripts/day21/data/system-design-primer.md --strategy fixed`, затем то же самое с `--strategy structural`, затем `bun run src/main.ts eval` — и получает готовый отчёт для коммита.

## User Stories

1. As a developer, I want to index a markdown file using a fixed-size chunker, so that I have a baseline for comparison.
2. As a developer, I want to index the same markdown file using a structural markdown chunker, so that I can compare structural vs fixed-size strategies.
3. As a developer, I want each chunk to carry metadata (strategy, source file, document title, section breadcrumb, chunk index, char offsets), so that I can trace retrieval results back to their origin.
4. As a developer, I want embeddings generated by a local Ollama model, so that I don't burn API credits and can work offline.
5. As a developer, I want to tune chunker parameters (chunk size, overlap, structural split threshold) via the `options` table in the database, so that I don't need to edit source code to experiment.
6. As a developer, I want reasonable hardcoded fallbacks for all indexing settings, so that the pipeline works out of the box on a fresh database.
7. As a developer, I want chunks and vectors persisted in SQLite via `sqlite-vec`, so that the index survives across runs and is ready for day 22 RAG.
8. As a developer, I want both strategies to coexist in the same index (distinguished by a `strategy` column), so that I can evaluate them side by side without rebuilding.
9. As a developer, I want a CLI command `index <file> --strategy <fixed|structural>` that runs the full indexing pipeline for one strategy, so that I can rebuild any slice in isolation.
10. As a developer, I want the `index` command to print chunk count, average chunk size, min/max size, and total time, so that I see basic statistics immediately.
11. As a developer, I want a CLI command `eval` that runs the test queries against both strategies and prints a comparison table, so that the experiment is reproducible with one command.
12. As a developer, I want 10 ground-truth test queries stored in a JSON file with expected section names and keywords, so that the evaluation is deterministic and reviewable.
13. As a developer, I want Recall@3 computed per strategy by checking if any of the top-3 retrieved chunks belongs to an expected section OR contains expected keywords, so that I have a clear binary signal per query.
14. As a developer, I want Mean Reciprocal Rank (MRR) computed per strategy, so that I reward strategies that rank the correct answer higher.
15. As a developer, I want the `eval` command to save its output to `scripts/day21/report.md`, so that the result is committed as part of the exercise.
16. As a developer, I want the report to contain a markdown table with both strategies side by side and 2–3 example queries with top-3 results, so that I can qualitatively sanity-check the quantitative metrics.
17. As a developer, I want the test corpus (system-design-primer README) committed to the repo along with an ATTRIBUTION.md file, so that the day is self-contained and CC BY 4.0 compliant.
18. As a developer, I want the structural chunker to detect the document's H1 as the `title` and build a breadcrumb of parent H2/H3 headings as the `section` field, so that metadata is meaningful for retrieval.
19. As a developer, I want the structural chunker to further split any `##` section that exceeds the configured size threshold by its `###` subheadings, so that no single chunk is disproportionately large.
20. As a developer, I want the fixed-size chunker to carry basic metadata (source, title extracted from the first H1, chunk index, char offsets) even though it does not know about sections, so that both strategies share the same metadata schema.
21. As a developer, I want `IndexingService` to depend only on the three ports (`Chunker`, `Embedder`, `VectorIndex`), so that it can be unit-tested with in-memory fakes.
22. As a developer, I want `OllamaEmbedder` to talk to Ollama via plain HTTP (no SDK), so that the integration is simple and traceable.
23. As a developer, I want the SQLite schema migration to create both the `chunks` table and the `chunk_vectors` virtual table on first run, so that the setup is idempotent.
24. As a developer, I want unit tests for both chunkers covering boundary cases (empty input, single small chunk, exact-size input, oversized structural sections), so that refactors don't silently break chunking.
25. As a developer, I want unit tests for `SqliteVectorIndex` using synthetic unit vectors, so that upsert and search behavior is verified without Ollama.
26. As a developer, I want a unit test for `IndexingService` with mocked ports, so that the orchestration logic is verified in isolation.
27. As a developer, I want the live end-to-end run (real Ollama, real document, real report) to be executed manually via the CLI, so that CI and unit tests never depend on external services.
28. As a developer, I want the final `report.md` committed to the repo, so that the comparison result is visible in git history.

## Implementation Decisions

### Architecture

- Гекс-архитектура, как во всех предыдущих днях. Доменный слой ничего не знает ни про SQLite, ни про Ollama, ни про markdown. Три новых порта: `Chunker`, `Embedder`, `VectorIndex`. Доменный сервис `IndexingService` композит их.
- Новые модули группируются по существующим слоям — модели в `domain/models`, порты в `domain/ports`, сервисы и реализации чанкеров в `domain/services`, реализация `VectorIndex` в `storage/sqlite`, реализация `Embedder` в `api/ollama`.
- CLI-команды подключаются к существующему механизму команд проекта.

### Corpus

- Корпус: `system-design-primer/README.md` (английская версия), ~109 KB, ~40 страниц, 29× `##`, 82× `###`, 33× `####`. Лицензия CC BY 4.0.
- Файл кладётся в `scripts/day21/data/system-design-primer.md`. Рядом — `ATTRIBUTION.md` с указанием автора, источника, лицензии и даты скачивания.

### Chunking

- **FixedSizeChunker.** Единица измерения — символы (не токены), чтобы не тащить токенизатор bge-m3 и иметь детерминированное поведение. Дефолты: 1500 символов, overlap 200. Алгоритм: скользящее окно с шагом `size - overlap`. Для каждого чанка фиксируются `char_start`, `char_end`, `chunk_index`. Метаданные `title` извлекаются из первого H1 документа; `section` остаётся пустой.
- **StructuralMarkdownChunker.** Минимальный парсер markdown-заголовков построчно (без полноценной библиотеки — достаточно регулярок для `^#+ `). Алгоритм:
  1. Поддерживаем стек текущих заголовков (H1 → title, H2/H3 → breadcrumb).
  2. Первично режем по `##`: каждая секция от одного `##` до следующего (или до `#`) — отдельный чанк.
  3. Если размер чанка > `structural.maxSize` (дефолт 2000 символов), дорезаем его по `###` внутри.
  4. Пустые секции отбрасываются.
  5. Метаданные: `title` = H1, `section` = `"H2"` или `"H2 > H3"`, `char_start`/`char_end` — по исходному файлу, `chunk_index` — порядковый в рамках стратегии.

### Metadata schema

Единая для обеих стратегий:

- `id` — автоинкремент
- `strategy` — `'fixed' | 'structural'`
- `source` — путь к исходному файлу
- `title` — H1 документа (опционально)
- `section` — breadcrumb (опционально, только у структурной стратегии)
- `chunk_index` — порядковый номер чанка в рамках стратегии
- `char_start`, `char_end` — смещения в исходном файле
- `text` — собственно текст чанка

### Storage

- SQLite + расширение `sqlite-vec` (загружается через `loadExtension`).
- Таблица `chunks` — обычная, хранит метаданные и текст.
- Виртуальная таблица `chunk_vectors USING vec0(chunk_id INTEGER PRIMARY KEY, embedding float[1024])` — хранит эмбеддинги.
- Поиск: сначала `MATCH` по `chunk_vectors` с фильтром по `strategy` через JOIN с `chunks`, затем `ORDER BY distance LIMIT k`.
- Миграция создаётся как новая миграция в существующем механизме миграций проекта.

### Embeddings

- Модель: `bge-m3` (Ollama, 1024 dim, мультиязычная, контекст 8192 токена).
- Взаимодействие: HTTP POST на `{baseUrl}/api/embeddings` (или `/api/embed`, в зависимости от текущей версии Ollama — определяется на старте). Никакого SDK.
- Батчинг: эмбеддер отправляет чанки по одному или небольшими батчами; конкретный размер батча — деталь реализации, главное — есть интеграционный контракт «массив → массив той же длины в том же порядке».
- Настройки: `indexing.embeddings.provider`, `indexing.embeddings.model`, `indexing.embeddings.baseUrl`, `indexing.embeddings.dim` — всё через `options`-таблицу с фолбэками.

### Settings

Все настройки индексации живут в существующей таблице `options` (KV). Ключи:

- `indexing.chunk.fixed.size` (default 1500)
- `indexing.chunk.fixed.overlap` (default 200)
- `indexing.chunk.structural.primaryLevel` (default 2)
- `indexing.chunk.structural.splitLevel` (default 3)
- `indexing.chunk.structural.maxSize` (default 2000)
- `indexing.embeddings.provider` (default `ollama`)
- `indexing.embeddings.model` (default `bge-m3`)
- `indexing.embeddings.baseUrl` (default `http://localhost:11434`)
- `indexing.embeddings.dim` (default 1024)

Код читает значение через `SqliteOptionsRepository.get(key)` и применяет парсинг/фолбэк.

### Evaluation

- 10 запросов в `scripts/day21/test-queries.json`, формат:
  ```
  { "id": "q01",
    "query": "...",
    "expected_section_contains": ["Cache-aside", "Write-through"],
    "expected_keywords": ["cache-aside", "write-through", "lazy load"] }
  ```
- Запрос считается «попавшим», если хотя бы один из top-3 чанков удовлетворяет условию: либо `section` содержит одну из подстрок `expected_section_contains`, либо `text` содержит одно из `expected_keywords` (case-insensitive).
- **Recall@3** = доля запросов, где условие выполнено.
- **MRR** = среднее по запросам от `1 / rank_first_hit`, где `rank_first_hit` — позиция первого удовлетворяющего чанка (1..3), либо 0 если ни один не подошёл.
- Запросы эмбеддятся тем же `bge-m3`.

### CLI

Две команды:

- `index <file> --strategy <fixed|structural>` — запускает `IndexingService` с выбранной стратегией. Печатает: количество чанков, средний/мин/макс размер, общее время.
- `eval` — читает `test-queries.json`, гоняет retrieval для обеих стратегий, печатает markdown-табличку и сохраняет её в `scripts/day21/report.md`. Предполагает, что обе стратегии уже проиндексированы.

Обе команды подключаются к существующему роутеру CLI-команд проекта.

### Report format

Markdown-файл с двумя разделами:

1. **Summary table** — строки = стратегии (`fixed`, `structural`), колонки = `chunks`, `avg_size`, `min_size`, `max_size`, `index_time_ms`, `recall@3`, `MRR`.
2. **Qualitative examples** — 2–3 запроса, для каждого — top-3 результата от каждой стратегии с `section` и первыми ~150 символами `text`.

## Testing Decisions

### Philosophy

Хорошие тесты проверяют внешнее поведение модуля через его публичный интерфейс, а не внутренности. Мокаются только порты на границе (HTTP к Ollama, файловая система для чтения корпуса в e2e). Доменные чанкеры — чистые функции, тестируются без моков вообще.

### What gets tested

- **`FixedSizeChunker`** — юнит-тесты:
  - Пустой вход → ноль чанков.
  - Вход меньше `size` → один чанк целиком.
  - Вход, кратный `size - overlap` → ровное количество чанков с корректными `char_start`/`char_end`.
  - Overlap реально пересекается между соседями.
  - `title` извлекается из первой строки `# ...`, если есть.
- **`StructuralMarkdownChunker`** — юнит-тесты:
  - Документ без заголовков → один чанк, пустая секция.
  - Документ с H1 + двумя H2 → два чанка, корректный breadcrumb, корректный `title`.
  - Секция больше `maxSize` с H3 внутри → дорезается по H3.
  - Секция больше `maxSize` без H3 внутри → возвращается как один большой чанк (акт осознанного компромисса, фиксируем в тесте).
  - `char_start`/`char_end` соответствуют исходным смещениям.
- **`SqliteVectorIndex`** — юнит-тесты (настоящая in-memory SQLite с реально загруженным `sqlite-vec`):
  - `upsert` нескольких чанков с синтетическими единичными векторами `[1,0,0,...]`, `[0,1,0,...]`, `[0,0,1,...]`.
  - `search` с вектором, близким к первому, возвращает его первым.
  - Фильтр по `strategy` действительно возвращает только чанки нужной стратегии.
  - Повторный `upsert` того же чанка не дублирует записи.
- **`IndexingService`** — юнит-тест с фейковыми реализациями всех трёх портов:
  - Читает текст, передаёт в чанкер, передаёт чанки в эмбеддер, передаёт пары (чанк, вектор) в индекс — всё в правильном порядке и без потерь.
- **`OllamaEmbedder`** — юнит-тест с моком `fetch` (проверяется, что запрос формируется правильно и ответ парсится корректно). Никаких реальных HTTP-вызовов.

### What does NOT get tested automatically

- Реальный прогон по system-design-primer с реальным Ollama и реальным отчётом — делается вручную через CLI перед финальным коммитом. Это и есть критерий приёмки дня: в репо лежит закоммиченный `report.md`, который автор воспроизвёл локально.
- CLI-команды `index` и `eval` как таковые — тонкая обёртка вокруг сервиса, покрывается ручным прогоном.

### Prior art

В проекте уже есть похожие типы тестов, на которые можно опираться:

- Юнит-тесты репозиториев SQLite (`*-repository.test.ts`) — пример работы с реальной in-memory SQLite.
- Юнит-тесты доменных сервисов с моками (`strategy.test.ts`, `scheduler.test.ts`) — пример тестирования оркестраторов через фейковые реализации портов.
- Тесты репозитория сообщений и профилей — пример сохранения/чтения структурированных данных со schema migration.

Стиль и шаблон тестов копируем из существующих `*.test.ts` файлов.

## Out of Scope

- **RAG как таковой.** Мы строим индекс и сравниваем стратегии, но не реализуем retrieval-augmented генерацию ответа. Это день 22.
- **Третья и далее стратегии chunking** (sentence splitter, semantic chunking, recursive character splitter). Ограничиваемся двумя для честного попарного сравнения.
- **Поддержка PDF, HTML, DOCX.** Только markdown. Расширение форматов — отдельная задача.
- **Ре-эмбеддинг при изменении настроек.** Если пользователь поменял `chunk.fixed.size` и перезапустил `index`, старые чанки со старыми размерами не удаляются автоматически — пользователь должен пересоздать индекс вручную (удалить строки/файл). Это разумно для учебного пайплайна, не для прода.
- **Гибридный поиск (BM25 + vector).** Только чистый векторный поиск.
- **Инкрементальная индексация** (переиндексировать только изменившиеся части файла). Всегда полная переиндексация.
- **Более сложные метрики** — NDCG, Precision@k с градуированной релевантностью. Recall@3 + MRR достаточно для сравнения двух стратегий на 10 запросах.
- **UI для просмотра чанков.** Только CLI.
- **Нефункциональные требования по производительности.** На 40 страниц любая реализация отработает за секунды, оптимизация не нужна.

## Further Notes

- **Воспроизводимость.** Корпус коммитится в репо → одна и та же версия документа у всех. Запросы коммитятся в репо. Отчёт коммитится в репо. Модель эмбеддингов фиксирована (`bge-m3`). Единственный неконтролируемый фактор — версия Ollama и сам bge-m3 (Ollama может обновить веса). Это приемлемо для учебного задания.
- **Атрибуция.** `system-design-primer` распространяется под CC BY 4.0. В `scripts/day21/data/ATTRIBUTION.md` указываем автора (Donne Martin), ссылку на оригинал, лицензию, дату скачивания.
- **Зависимость `sqlite-vec`.** Добавляет одну новую зависимость (`bun add sqlite-vec`). Prebuilt-бинарник под Linux x64 подтягивается автоматически. Если `loadExtension` в Bun SQLite даст сбой — первым шагом фазы 2 будет diagnostic run с минимальным воспроизведением и фолбэк на ручной косинус в JS (интерфейс `VectorIndex` при этом не меняется).
- **Будущее подключение дня 22 RAG.** Поскольку `VectorIndex` — это порт, день 22 подключит `search` к генерации ответа без изменений в хранилище. `IndexingService` при этом не трогаем.
- **Язык документации.** PRD и план — на русском (как все предыдущие дни). User stories — на английском по шаблону скилла. Отчёт `report.md` — на английском (консистентно с исходным документом).
- **Порядок фаз реализации** (оформляется отдельным планом через `prd-to-plan`):
  1. PRD + план.
  2. SQLite-миграция + `VectorIndex` порт/реализация + тесты.
  3. Оба чанкера + тесты.
  4. `OllamaEmbedder` + тест с моком `fetch`.
  5. `IndexingService` + тест с фейковыми портами.
  6. CLI-команда `index`.
  7. CLI-команда `eval` + `test-queries.json`.
  8. Живой прогон → `report.md` → финальный коммит.
