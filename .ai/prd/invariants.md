## Problem Statement

Ассистент не имеет механизма ограничений, которые он обязан соблюдать. Пользователь может задать архитектурные решения, ограничения по стеку или бизнес-правила — но ассистент не знает о них и может предложить решения, которые их нарушают. Нужен способ задать инварианты, которые ассистент будет явно учитывать в рассуждениях и отказываться нарушать.

## Solution

Добавить систему инвариантов, привязанных к профилю пользователя. Инварианты — это правила/ограничения, которые инжектируются в system prompt перед каждым LLM-запросом. Ассистент получает явную инструкцию: проверять свой ответ на соответствие инвариантам и отказывать, если запрос пользователя им противоречит, с объяснением причины отказа.

## User Stories

1. As a пользователь, I want добавить инвариант через `/invariant add <текст>`, so that ассистент знал о моих ограничениях.
2. As a пользователь, I want видеть список всех инвариантов через `/invariant list`, so that я мог проверить, что задано.
3. As a пользователь, I want удалить инвариант через `/invariant delete <id>`, so that я мог убрать устаревшие ограничения.
4. As a пользователь, I want чтобы инварианты были привязаны к моему профилю, so that разные профили имели разные наборы ограничений.
5. As a пользователь, I want чтобы ассистент видел инварианты в каждом запросе, so that он учитывал их в рассуждениях.
6. As a пользователь, I want чтобы ассистент отказывал мне, если мой запрос противоречит инварианту, so that я не мог случайно нарушить свои же правила.
7. As a пользователь, I want чтобы при отказе ассистент объяснял, какой именно инвариант нарушен и почему, so that я понимал причину.
8. As a пользователь, I want чтобы без активного профиля инварианты не применялись, so that система не ломалась при отсутствии профиля.
9. As a пользователь, I want чтобы при переключении профиля менялись и инварианты, so that каждый профиль имел свой контекст.

## Implementation Decisions

### Хранение

- Новая таблица `invariants` в SQLite: `id`, `profile_id` (FK → profiles), `content` (текст инварианта), `created_at`.
- Каскадное удаление при удалении профиля.

### Domain-слой

- Новый порт `InvariantRepository` с методами: `add(profileId, content)`, `getByProfile(profileId)`, `delete(id)`.
- `InvariantService` — тонкий сервис поверх репозитория (CRUD). Метод `buildInvariantsBlock(profileId)` форматирует инварианты для инжекции в промпт.
- `ProfileService.buildProfileBlock()` дополняется вызовом `InvariantService` для добавления блока инвариантов (или `ChatService` собирает оба блока отдельно).

### Инжекция в промпт

- `ChatService.sendMessage()` получает блок инвариантов из `InvariantService` и добавляет его в `instructions` вместе с профилем.
- Формат блока:

```
=== ИНВАРИАНТЫ (нарушение запрещено) ===
Ты ОБЯЗАН соблюдать следующие инварианты. Если запрос пользователя противоречит любому из них — ОТКАЖИ и объясни, какой инвариант будет нарушен и почему.

1. <текст инварианта>
2. <текст инварианта>
...
=========================================
```

### REPL-команды

- `/invariant` — показать список инвариантов активного профиля.
- `/invariant add <текст>` — добавить инвариант.
- `/invariant delete <id>` — удалить инвариант по ID.

Если нет активного профиля — сообщение "Сначала создайте профиль".

### Поведение при конфликте

Ассистент сам обнаруживает конфликт через инструкции в system prompt. Отдельного LLM-вызова для валидации нет — это делается через формулировку промпта, которая обязывает модель проверять инварианты перед ответом.

## Testing Decisions

Тесты проверяют внешнее поведение, а не детали реализации.

### Что тестируем

- **InvariantRepository** (SQLite): CRUD-операции, каскадное удаление с профилем. По аналогии с `profile-repository.test.ts`.
- **InvariantService**: `buildInvariantsBlock()` — форматирование блока для пустого списка, одного и нескольких инвариантов.
- **ChatService**: инварианты попадают в `instructions` LLM-запроса (через capturing client, по аналогии с тестом профилей в `chat-service.test.ts`).
- **REPL handleCommand**: `/invariant add`, `/invariant list`, `/invariant delete` — по аналогии с тестами `/profile` в `index.test.ts`.

### Что НЕ тестируем

- Что LLM действительно отказывает при конфликте — это поведение модели, не кода.

## Out of Scope

- Автоматическая валидация ответа LLM на соответствие инвариантам (отдельный LLM-вызов).
- Категории/теги для инвариантов.
- Импорт/экспорт инвариантов.
- Инварианты вне профиля (глобальные).

## Further Notes

Инварианты — это "жёсткие" правила, в отличие от preferences профиля. Preferences описывают стиль и формат, инварианты — запреты и ограничения, которые нельзя нарушать.
