# Task State Machine

## Problem Statement

Агент ведёт диалог с пользователем, но не имеет формализованного понимания, на каком этапе находится работа над задачей. Это приводит к нескольким проблемам:

- При возврате в сессию после паузы агент не знает, на чём остановились — пользователю приходится повторно объяснять контекст.
- Агент не различает фазы работы (планирование, выполнение, проверка) и может смешивать их — например, начать писать код до согласования плана.
- Нет способа отследить прогресс по задаче: что уже сделано, что осталось.
- В рамках одной сессии невозможно вести несколько задач с независимым прогрессом.

## Solution

Ввести понятие **Task** (задача) как сущность внутри сессии. Каждая задача проходит через конечный автомат состояний:

```
planning → execution → validation → done
```

С возможностью откатов:
- `validation → execution` (если валидация не прошла)
- `execution → planning` (если нужно переосмыслить подход)

Дополнительные состояния:
- `paused` — задача приостановлена (явно или при уходе из сессии)
- `cancelled` — задача отменена

Каждая фаза имеет свой системный промпт, который направляет поведение LLM. Агент сам определяет момент перехода между фазами, но код явно валидирует допустимость перехода.

В каждый момент в сессии **активна только одна задача**. Остальные находятся в состоянии `paused`.

При возврате в сессию агент показывает сохранённое резюме активной задачи — без повторных объяснений и без траты токенов на генерацию.

Задачи создаются двумя способами:
- Явно через команду `/task create "описание"`
- Автоматически: LLM определяет, что пользователь ставит задачу, и **запрашивает подтверждение** перед созданием.

## User Stories

1. As a user, I want to create a task explicitly via `/task create "description"`, so that the agent starts working on it in a structured way.
2. As a user, I want the agent to detect when I'm describing a new task and ask me to confirm creation, so that tasks are tracked without me always using commands.
3. As a user, I want each task to go through planning phase first, so that the agent asks clarifying questions and proposes a plan before jumping to implementation.
4. As a user, I want to see the current task state (phase, current step, expected action) via `/task`, so that I always know where we are.
5. As a user, I want the agent to automatically transition between phases when appropriate, so that the workflow feels natural, not bureaucratic.
6. As a user, I want the code to validate state transitions, so that the agent can't skip phases or make nonsensical jumps.
7. As a user, I want the agent to be able to go back from validation to execution if issues are found, so that we can fix problems without starting over.
8. As a user, I want the agent to be able to go back from execution to planning if the approach needs rethinking, so that we don't waste effort on a wrong path.
9. As a user, I want to pause a task explicitly via `/task pause`, so that I can switch context without leaving the session.
10. As a user, I want all active tasks to be automatically paused when I exit the session or switch to another session, so that nothing is lost.
11. As a user, I want to resume a paused task and see a summary of where we left off, so that I can continue without re-explaining the context.
12. As a user, I want the summary to be stored in the database (not regenerated by LLM), so that resumption is instant and doesn't cost tokens.
13. As a user, I want to have multiple tasks in one session, so that I can track different pieces of work independently.
14. As a user, I want only one task to be active at a time, so that the agent stays focused and prompts don't conflict.
15. As a user, I want to switch between tasks via `/task switch`, so that I can pick up any paused task.
16. As a user, I want to cancel a task via `/task cancel`, so that I can abandon work that's no longer needed.
17. As a user, I want to list all tasks in the session via `/task list`, so that I can see the full picture of ongoing work.
18. As a user, I want the agent's behavior to change depending on the current phase, so that planning focuses on questions and design, execution focuses on implementation, and validation focuses on checking results.
19. As a user, I want to see what step we're on and what action is expected next, so that the collaboration feels structured.
20. As a user, I want the task state to persist across REPL restarts, so that I don't lose progress.
21. As a user, I want to see a welcome-back summary when I return to a session with active/paused tasks, so that I immediately know where I left off.
22. As a user, I want completed tasks to remain in the list (as `done`), so that I can review what was accomplished in this session.

## Implementation Decisions

### Domain Model: Task

Новая сущность `Task` со следующими полями:
- `id` — уникальный идентификатор
- `sessionId` — привязка к сессии
- `title` — краткое описание задачи
- `phase` — текущая фаза: `planning | execution | validation | done | paused | cancelled`
- `previousPhase` — фаза до паузы (для корректного resume)
- `currentStep` — свободный текст, описание текущего шага
- `expectedAction` — свободный текст, что ожидается дальше
- `summary` — резюме состояния (обновляется при каждом переходе фазы)
- `createdAt`, `updatedAt` — временные метки

### Модуль: TaskStateMachine

Чистая логика валидации переходов. Не зависит ни от чего — принимает текущую фазу и целевую фазу, возвращает `boolean`.

Допустимые переходы:
```
planning   → execution, paused, cancelled
execution  → validation, planning, paused, cancelled
validation → done, execution, paused, cancelled
paused     → planning, execution, validation (возврат в previousPhase)
done       → (терминальное состояние, переходов нет)
cancelled  → (терминальное состояние, переходов нет)
```

### Модуль: TaskRepository (порт + SQLite-адаптер)

Интерфейс:
- `create(sessionId, title): Task`
- `findById(id): Task | null`
- `findBySessionId(sessionId): Task[]`
- `findActive(sessionId): Task | null`
- `update(task): void`

Новая таблица `tasks` в SQLite.

### Модуль: TaskService

Бизнес-логика:
- `createTask(sessionId, title)` — создаёт задачу в фазе `planning`, делает её активной (паузит предыдущую активную)
- `transition(taskId, targetPhase)` — валидирует переход через TaskStateMachine, обновляет фазу, сохраняет `previousPhase` при паузе
- `pauseTask(taskId)` — переводит в `paused`, сохраняет `previousPhase`
- `resumeTask(taskId)` — возвращает в `previousPhase`, паузит текущую активную задачу
- `cancelTask(taskId)` — переводит в `cancelled`
- `updateStep(taskId, currentStep, expectedAction)` — обновляет текущий шаг
- `updateSummary(taskId, summary)` — обновляет резюме
- `pauseAllActive(sessionId)` — паузит все активные задачи сессии (при выходе)
- `getSessionTasks(sessionId)` — список задач сессии
- `getActiveTask(sessionId)` — текущая активная задача

### Интеграция с ChatService

ChatService при формировании запроса к LLM:
1. Проверяет наличие активной задачи в сессии
2. Если есть — добавляет фазовый промпт в системное сообщение
3. Добавляет контекст задачи (title, currentStep, expectedAction) в системное сообщение
4. Анализирует ответ LLM на предмет:
   - Предложения перехода фазы (LLM включает специальный маркер в ответ)
   - Обновления currentStep/expectedAction
   - Обновления summary
5. Если нет активной задачи — анализирует, не ставит ли пользователь новую задачу (автодетект)

### Маркеры переходов в ответе LLM

LLM сигнализирует о переходе через JSON-блок в конце ответа:

```
<!--task-update
{"transition": "execution", "currentStep": "...", "expectedAction": "...", "summary": "..."}
-->
```

ChatService парсит этот блок, валидирует переход через TaskStateMachine и применяет изменения. Блок удаляется из ответа перед показом пользователю.

### Маркер автодетекта новой задачи

Если нет активной задачи, LLM может предложить создание:

```
<!--task-detect
{"title": "..."}
-->
```

ChatService показывает пользователю подтверждение: "Похоже, вы ставите задачу: X. Создать? (y/n)"

### Фазовые промпты

**planning:**
```
Ты на этапе ПЛАНИРОВАНИЯ задачи: "{title}".
Текущий шаг: {currentStep}

Твои обязанности на этом этапе:
- Задавай уточняющие вопросы, пока не будет полной ясности
- Предложи план реализации по шагам
- НЕ пиши код и НЕ реализуй ничего на этом этапе
- Когда план согласован с пользователем — переходи к execution

Когда готов перейти к следующему этапу или нужно обновить шаг, добавь в конец ответа блок:
<!--task-update
{"transition": "execution"|null, "currentStep": "новый шаг", "expectedAction": "что дальше", "summary": "краткое резюме"}
-->
```

**execution:**
```
Ты на этапе ВЫПОЛНЕНИЯ задачи: "{title}".
Текущий шаг: {currentStep}
Ожидаемое действие: {expectedAction}

Твои обязанности на этом этапе:
- Следуй согласованному плану
- Реализуй текущий шаг
- Если подход не работает — можешь вернуться к planning
- Когда реализация завершена — переходи к validation

Когда готов перейти к следующему этапу или нужно обновить шаг, добавь в конец ответа блок:
<!--task-update
{"transition": "validation"|"planning"|null, "currentStep": "новый шаг", "expectedAction": "что дальше", "summary": "краткое резюме"}
-->
```

**validation:**
```
Ты на этапе ПРОВЕРКИ задачи: "{title}".
Текущий шаг: {currentStep}
Ожидаемое действие: {expectedAction}

Твои обязанности на этом этапе:
- Проверь результат: соответствует ли он плану?
- Выяви проблемы, баги, несоответствия
- Если есть проблемы — вернись к execution с описанием что исправить
- Если всё хорошо — переходи к done

Когда готов перейти к следующему этапу или нужно обновить шаг, добавь в конец ответа блок:
<!--task-update
{"transition": "done"|"execution"|null, "currentStep": "новый шаг", "expectedAction": "что дальше", "summary": "краткое резюме"}
-->
```

**Промпт автодетекта (когда нет активной задачи):**
```
У пользователя нет активной задачи. Если пользователь описывает задачу или просит что-то реализовать/исправить/сделать, предложи создать задачу, добавив в конец ответа блок:
<!--task-detect
{"title": "краткое название задачи"}
-->
Если это просто вопрос или беседа — не добавляй блок.
```

### REPL-команды

- `/task` — показать текущую активную задачу (фаза, шаг, ожидаемое действие, резюме)
- `/task create "описание"` — создать новую задачу
- `/task list` — список всех задач в сессии с их состояниями
- `/task pause` — приостановить текущую активную задачу
- `/task cancel` — отменить текущую активную задачу
- `/task switch` — показать список задач и переключиться на выбранную

### Восстановление сессии

При входе в сессию (переключение или запуск REPL):
1. Проверить наличие задач в сессии
2. Если есть активная задача — показать её резюме из БД
3. Если есть только paused задачи — показать список с резюме
4. Автоматически resume последней активной задачи

## Testing Decisions

Хороший тест проверяет **внешнее поведение**, а не внутреннюю реализацию. Тест должен оставаться зелёным при рефакторинге внутренностей, пока поведение не меняется.

### Модули для тестирования

**TaskStateMachine** (юнит-тесты):
- Все допустимые переходы возвращают `true`
- Все недопустимые переходы возвращают `false`
- Терминальные состояния (`done`, `cancelled`) не имеют переходов
- `paused` возвращается в корректную фазу
- Приоритет: высокий (чистая логика, быстрые тесты, критическая корректность)

**TaskRepository** (интеграционные тесты с SQLite):
- CRUD-операции
- `findActive` возвращает единственную активную задачу
- `findBySessionId` возвращает все задачи сессии
- Приоритет: средний (аналог существующих тестов репозиториев в проекте)

**TaskService** (юнит-тесты с моками репозитория):
- Создание задачи ставит предыдущую на паузу
- Переход фазы валидируется и применяется
- Пауза сохраняет previousPhase
- Resume восстанавливает previousPhase
- `pauseAllActive` паузит все активные
- Приоритет: высокий

**ChatService интеграция** (юнит-тесты):
- Фазовый промпт добавляется при наличии активной задачи
- Маркер `task-update` парсится и применяется
- Маркер `task-detect` парсится и генерирует подтверждение
- Невалидный переход в маркере отклоняется
- Приоритет: высокий

**REPL-команды** (юнит-тесты):
- Каждая команда вызывает правильные методы TaskService
- Корректный вывод для пользователя
- Приоритет: средний (аналог существующих тестов REPL)

### Prior art

Тесты в проекте следуют паттерну:
- Файлы `*.test.ts` рядом с модулем
- Bun test runner (`bun:test`)
- Моки через интерфейсы (порты)
- Примеры: `chat-service.test.ts`, `session-service.test.ts`, `session-repository.test.ts`

## Out of Scope

- Вложенные задачи / подзадачи — задача плоская, без иерархии
- Зависимости между задачами
- Кросс-сессионные задачи (задача привязана к одной сессии)
- Пользовательская настройка фаз (набор фаз фиксирован)
- Визуализация прогресса (прогресс-бар и т.п.)
- Экспорт/импорт задач
- Приоритеты и дедлайны задач

## Further Notes

- Миграция БД: добавление таблицы `tasks` должно быть обратно совместимым — существующие сессии без задач продолжают работать как раньше.
- Если в сессии нет активной задачи, агент работает в обычном режиме (как сейчас) + промпт автодетекта.
- Маркер `<!--task-update-->` выбран как HTML-комментарий, чтобы не ломать рендеринг если случайно попадёт в вывод.
- Резюме обновляется при каждом переходе фазы, а также может обновляться LLM в рамках `task-update` блока.
